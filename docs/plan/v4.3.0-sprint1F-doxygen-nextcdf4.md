# V4.3.0 Sprint 1F: Doxygen and Code Documentation for src/nextcdf4

Source: docs/roadmap.md, "V4.3.0 / Sprint 1F".

## Goal

Every function, type, and file under `src/nextcdf4/` carries real
Doxygen documentation that doxygen renders and checks, instead of the
plain `/*` comment blocks it currently ignores. Non-obvious code has
in-body comments explaining why it does what it does. The Doxyfile
`INPUT` list also picks up the `src/` files that were never added to
it, so their existing Doxygen blocks finally render. The `docs`
target and the CI documentation job stay warning-free throughout.

## Decisions

| Topic | Decision |
| --- | --- |
| Scope | "All code in src" means `src/nextcdf4/` plus the handful of genuinely undocumented functions in top-level `src/` (Ed: the jpeg-lossless codec functions). `#else !HAVE_*` stub functions and `#if 0` dead code are documented no further than they already are. `include/`, `test/` and `examples/` are not documentation targets. (Ed: 1-other + follow-ups) |
| NEXTCDF-4 comment style | Convert every `/*` documentation block in `src/nextcdf4/*.c` to `/**` and complete `@param`/`@return`/`@retval`. Purely internal "why" comments stay `/*`. (Ed: 2a) |
| Doxyfile INPUT | Add all `src/` files currently missing from `INPUT` plus NEP-owned `include/nep_logging.h`. (Ed: 3a) |
| "Why" comments | Targeted rationale comments where the code is non-obvious: HDF5 idioms, ownership/refcount rules, format quirks, workarounds. Self-evident lines get nothing. (Ed: 4a) |
| Enforcement | Keep `EXTRACT_ALL=YES` and `WARN_AS_ERROR=YES`; rely on the existing warning-free docs build. `WARN_IF_UNDOCUMENTED` cannot be enabled without `EXTRACT_ALL=NO`, which would also demand full docs for every file under `examples/` (already in `INPUT`) — out of scope. |

## Work items

### 1. Convert `nxt4meta.c` documentation blocks

`src/nextcdf4/nxt4meta.c` (3062 lines, ~81 plain `/*` blocks, ~58
function definitions).

- For each `/*` block that documents a function, variable, or
  constant, change the opening to `/**` and complete the block:
  keep the existing `@brief`/prose, add `@param` for every parameter,
  `@return` for non-void returns (`@retval` only when listing
  specific codes adds clarity, matching `nxt4internal.h` style).
- Leave section-marker comments and in-body rationale comments as
  `/*`.
- Document the few definitions that have no comment at all (e.g.
  helpers such as `free_name_list()` at ~line 60, `reserved_atts[]`
  at ~line 19) — `static` functions are rendered because
  `EXTRACT_STATIC=YES`, so they need the same treatment.
- Sanity-check each block against the signature it precedes; some
  `/*` blocks may document stale parameter lists.
- Add targeted in-body "why" comments where the HDF5 or metadata
  logic is non-obvious (see work item 4 for the bar).

### 2. Convert the remaining `src/nextcdf4/*.c` files

Same rules as work item 1, per file:

- `nxt4file.c` — 15 blocks / 14 functions (`NEXTCDF4_free_file`,
  `NEXTCDF4_add_file`, `NEXTCDF4_get_file`, marker I/O, etc.).
- `nxt4io.c` — 9 blocks / ~10 functions (hyperslab I/O, memtype
  checks). Keep its 3 existing `/**` blocks as-is.
- `nxt4type.c` — 8 blocks / 26 functions (type mapping, small-float
  and user-defined type helpers).
- `nxt4group.c` — 6 blocks / 12 functions.
- `nxt4dispatch.c` — 4 blocks / ~3 functions (dispatch table,
  initialize/finalize).
- `nxt4create.c` — 2 blocks / 2 functions.
- `nxt4open.c` — 1 block / 1 function.

### 3. Complete header documentation

- `nxt4internal.h`: it already has ~40 `/**` blocks; audit all
  `NEXTCDF4_*` prototypes, structs (`NEXTCDF4_FILE_INFO_T` etc.),
  macros, and enum/typedef members and add blocks where missing.
  Convert its 3 `/*` doc blocks.
- `nxt4err.h`: already fully `/**` — verify only.

### 4. Targeted "why" comments

While editing each file, add short in-body `/*` comments explaining
non-obvious decisions, in particular:

- HDF5 idiom choices (scale attachment order, `H5Fget_obj_count`
  leak checks, datatype copy/close ownership).
- Ownership/refcount rules for `NC_FILE_INFO_T` vs
  `NEXTCDF4_FILE_INFO_T`.
- NEXTCDF-4 format quirks (reserved attribute names, marker
  attributes, dimid/varid encoding).
- Workarounds and deliberate deviations from netcdf-c's netcdf-4
  backend.

Do not comment self-evident statements.

### 6. Document the undocumented non-stub functions in top-level `src/`

Give full `/**` blocks (brief, `@param`, `@return`) to the real
functions that currently have none:

- `dicom_jpeg_lossless_precision()` in
  `src/dicomjpeglosslessprecision.c` (SOF-marker scan that returns
  the sample precision).
- In `src/dicomjpeglosslessimpl.inc.c` (the shared template included
  by the 8/12/16-bit decoders): `dicom_ll_init_source`,
  `dicom_ll_fill_input_buffer`, `dicom_ll_skip_input_data`,
  `dicom_ll_term_source`, `dicom_ll_mem_src`, and
  `DICOM_LL_DECODE_FUNC_NAME`. Document the libjpeg source-manager
  contract (callback semantics, the synthetic EOI buffer) rather than
  restating the one-line bodies.

Do **not** add doc blocks to the feature-disabled stubs —
`NC_DICOM_get_vara` in `src/dicomfile.c` (`#else !HAVE_DICOM`) and
`dicom_jpeg_lossless_decode{8,12,16}` in
`src/dicomjpeglossless{8,12,16}.c` (`#else !HAVE_DICOM_LOSSLESS`) —
or to `#if 0` dead code such as `cdf_read_dim` in `src/cdffile.c`.

## Verification

Local:

```sh
rm -rf build && cmake -S . -B build \
    -DNEP_BUILD_DOCUMENTATION=ON -DBUILD_TESTING=OFF
cmake --build build --target docs 2>&1 | tee doc_build.log
! grep -i warning doc_build.log
```

Then a normal build to prove the comment changes broke nothing:

```sh
rm -rf build && cmake -S . -B build -DNEP_ENABLE_NEXTCDF4=ON \
    -DCMAKE_PREFIX_PATH="/usr/local/netcdf-c;/usr/local/hdf5-2.1.1"
cmake --build build -j
ctest --test-dir build --output-on-failure
```

- `build/docs/html/` renders: spot-check that `nxt4meta.c` functions
  (e.g. `NEXTCDF4_load_metadata`) show their `@brief`/`@param` text.
- `ctest` passes exactly as before — the sprint changes no code
  behavior.

CI: the `ci.yml` documentation step must pass its "warning" grep;
all existing jobs stay green. `deploy-docs.yml` is unaffected but
will pick the new pages up on the 4.3.0 release.
