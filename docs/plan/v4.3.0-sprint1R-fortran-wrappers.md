# v4.3.0 Sprint 1R: Fortran Wrappers

Source: docs/roadmap.md, "V4.3.0 - NEXTCDF4 Development / Sprint 1R".

## Goal

Fortran applications can explicitly select NEXTCDF-4, define its new atomic types, and exchange binary16/bfloat16 buffers through an installed, documented module with familiar NetCDF-Fortran conventions. The binding preserves C conversion/error behavior and existing C/file compatibility. Normal NEXTCDF-4 CI verifies both build-tree use and a separately built installed consumer. Reference wrappers and full Fortran representations for every enhanced type are explicitly deferred rather than implied by the original same-release goal.

## Decisions

| Topic | Decision |
|---|---|
| Public package | `module nep_nextcdf4`, library/target `nepnextcdf4f`, exported target `NEP::nepnextcdf4f` (Ed accepted 1a). Do not revive compression's retired `nep.mod`/`libnepf`. |
| Small-float API | Four generics: `nf90_get_var_float16`, `nf90_put_var_float16`, `nf90_get_var_bfloat16`, `nf90_put_var_bfloat16`, scalar through rank 7, optional `start`, `count`, `stride` (Ed accepted 2a). |
| Representation | `integer(c_int16_t)` holds uninterpreted 16-bit encodings, not numeric integer samples or a new Fortran real kind. All bit patterns, including sign bits, survive raw I/O. |
| Conventions | File/group IDs unchanged; variable IDs and starts are 1-based; dimension vectors are in Fortran order and reversed for C. Preserve NetCDF status codes. |
| References | No reference value type, creators, dereferencing, token inquiries, cleanup or reference I/O wrappers in v4.3.0 (Ed accepted 3a). Export `nf90_std_ref` as a type constant only. |
| Other types | Export all new atomic constants; representative existing NetCDF-Fortran numeric, enum/compound metadata and character tests, not general raw/complex/user-type/string-value interfaces (Ed accepted 4a). Remove the obsolete claim that C user types/strings are still broken. |
| CI | Enable Fortran in the normal `nextcdf4` job and add installed-consumer coverage. Keep `nextcdf4-sanitizers` C-only, retaining its existing full suite (Ed accepted 5a). |
| Build gate | Build the module only when `NEP_ENABLE_NEXTCDF4=ON` and `NEP_ENABLE_FORTRAN=ON`. For this combination require NetCDF-Fortran >=4.6.2 and a working compiler/module; fail rather than silently omit the binding. Preserve existing reader-only discovery behavior. |
| Packaging | Reuse `+fortran`/`+nextcdf4`; update Spack install assertions/descriptions and version-gate new requirements for `main` and releases >=4.3.0. No new variant/plugin/cache-path option. Conda remains unchanged because it disables NEXTCDF-4. |
| Release | Sprint 2 owns release notes/tag/publication and the upstream Spack version-bump PR. NEXTCDF-4 remains experimental. |

## Work items

### 1. Add the installed module and exact public contract

Files: new `fsrc/CMakeLists.txt`, `fsrc/nep_nextcdf4.F90`, `fsrc/nep_nextcdf4_c.c`; root `CMakeLists.txt`, `NEPConfig.cmake.in`, `include/nep_meta.h.in` only if its existing Fortran description needs clarification.

Use a private-by-default module with these public integer parameters (default integer, usable by standard `nf90_*` calls):

- `nf90_nextcdf4 = ior(64, ishft(9,19))`, `nf90_netcdf4_model = 67108864`.
- `nf90_float16=17`, `nf90_bfloat16=18`, `nf90_float8_e4m3=19`, `nf90_float8_e5m2=20`, `nf90_float6_e2m3=21`, `nf90_float6_e3m2=22`, `nf90_float4_e2m1=23`, `nf90_complex=24`, `nf90_doublecomplex=25`, `nf90_bitfield8=26`, `nf90_bitfield16=27`, `nf90_bitfield32=28`, `nf90_bitfield64=29`, `nf90_std_ref=30`.

The C bridge includes installed public headers only and has build-time assertions matching every parameter to the corresponding C macro, including the UDF flag expression. A future encoding mismatch must fail the build, not silently open the wrong format. No configure-time executable or cross-compilation override is needed.

Public initialization: `integer function nf90_nextcdf4_initialize()` returns `nf90_noerr` if `NC_NEXTCDF4_initialize()` returns a non-NULL dispatch pointer, otherwise `nf90_einternal`. No finalize wrapper: do not unregister the process-wide dispatch while files may remain open. Standard `nf90_create/open/close` remain the file lifecycle API.

Generic signature for each `T = float16, bfloat16`:

```fortran
integer function nf90_put_var_T(ncid, varid, values, start, count, stride)
integer function nf90_get_var_T(ncid, varid, values, start, count, stride)
```

`ncid,varid` are default integer `intent(in)`; `values` is `integer(c_int16_t)` scalar or assumed-shape rank 1–7, `intent(in)` on put and `intent(inout)` on get (unselected/error elements must not become undefined). `start(:),count(:),stride(:)` are optional default-integer `intent(in)` vectors in Fortran order. Private specifics are named `nep_{get,put}_{float16,bfloat16}_{0..7}`. No `map`, attribute, `varm`, F77 or new real-kind overloads.

Use these deterministic selection rules:

- Inquire file-variable rank and dimension lengths before buffer access. Scalar specifics require scalar file variables; array rank must equal variable rank. Reject mismatches with `nf90_einval`.
- Default starts/strides are one; default counts are the array shape. With no selection options, require that shape matches the whole variable's current dimensions and use C `nc_{get,put}_var_T`. Appending unlimited dimensions requires explicit selection.
- Scalar/no selection uses C `var`; scalar with present empty selection vectors uses `var1` with NULL index. Nonempty vectors on scalars are invalid. Array selection with explicit count/stride uses `vara`/`vars`; array start-only with all extents one uses `var1`, otherwise `vara` with shape-derived counts. Thus all four C families are exercised without exposing four Fortran naming families.
- Present selection vectors must equal variable rank; starts >=1, counts >=0, strides >=1. Count in each dimension must not exceed the corresponding memory extent. Pack/unpack the leading `count` rectangle in Fortran order; untouched get elements retain their input values. Zero counts succeed after ID/type/selection validation without dereferencing a zero-sized buffer.
- Convert IDs and vector elements only after checking representability; preserve ncid, subtract one from varid and starts, reverse vectors, and use `c_size_t`/`c_intptr_t`-compatible C `size_t`/`ptrdiff_t` marshalling with a C size check. Check element-count/byte-count multiplication before allocation (`nf90_einval` on overflow, `nf90_enomem` on allocation failure). Invalid positive-ID/type/bounds cases use the C API's status; wrapper shape/vector errors use `nf90_einval`.
- Use contiguous owned temporary integer-bit buffers for all array calls, so noncontiguous sections work and C never receives a Fortran descriptor. Preserve exact bytes, including encodings above 32767; construct test patterns with `int(z'....',c_int16_t)`/`transfer`, not overflowing numeric conversion. Copy successful reads and completed `nf90_erange` reads back; do not scatter temporary buffers on structural/I/O failure. Writes retain C's completed-write range-warning behavior.
- No new rounding code: buffers already contain half encodings. Calls on matching half variables are raw; calls on `NC_FLOAT`/`NC_DOUBLE` retain existing C conversion rules. Existing standard `nf90_get/put_var` real buffers exercise typed C conversion separately.

Use private `bind(C)` interfaces for the bridge. For each C small-float function provide an internal `nep_f_*` counterpart with the same integer/selection arguments and `void *` buffer; cast only the pointer to the matching C type before forwarding. This avoids declaring C `_Float16`/`__bf16` as interoperable Fortran integer types. These are implementation symbols, not new installed C API declarations.

### 2. Build, installation and consumer exports

### 3. Focused tests and installed-consumer test

Files: `ftest/CMakeLists.txt`; new `ftest/ftst_nextcdf4_types.F90`, `ftest/ftst_nextcdf4_small_float.F90`, `ftest/nextcdf4_constants.c`, `ftest/installed_nextcdf4/CMakeLists.txt`, `ftest/installed_nextcdf4/consumer.F90`, `ftest/check_nextcdf4_install.cmake`.

Separate working directories prevent file collisions. Match existing runtime-path handling, including the new library. Register once through CTest, not again through `run_fortran_tests`.

Write failing interface/registration tests first. Required coverage:

- C/Fortran parity for all constants; explicit initialization succeeds without `.ncrc` autoload; standard create/open in native, NetCDF-4-model and classic-model modes reaches NEXTCDF-4.
- All 16 C small-float entry points reached via the four generics; scalar and ranks 1–7, asymmetric multidimensional shapes/order, strided file selections, noncontiguous memory sections, partial leading rectangles, zero-size selections, wrong ranks/vector lengths, invalid IDs/types, invalid starts/counts/strides and count/product overflow. Check exact statuses where backend validation applies.
- Both half types raw round-trip bit-exactly across close/reopen, including signed zero, infinities, NaNs and negative signed-integer representations of high-bit encodings. Test typed real32/real64 access through standard NetCDF-Fortran and half wrappers against standard float/double variables. Pin known encodings and a finite overflow returning `nf90_erange` with completed read results; reuse C test expectations rather than changing rounding policy.
- Fixed/unlimited dimensions with explicit append; small-float native coordinate variable; compatibility modes reject new types while standard numeric/character I/O succeeds. Standard enum/compound definition/inquiry/reopen metadata works in native and model modes and remains rejected in classic mode. `NC_CHAR` character data is not a test of `NC_STRING` value support.
- Installed consumer: CTest script installs into an isolated build-tree staging prefix, configures `ftest/installed_nextcdf4` in its own directory named `build` with only the installed NEP prefix and dependency prefixes, then builds/runs it. Consumer uses `find_package(NEP CONFIG REQUIRED)` and only `NEP::nepnextcdf4f`, imports the module, initializes, creates/writes/reopens/reads a small half dataset. Do not supply source/build-tree module paths or manually list NEP libraries. Fail on absent target/library/module.

## Out of scope

- Reference wrappers/value tokens/cleanup, including external references: beyond v4.3.0. The constant alone is supplied; callers must not treat an arbitrary byte array as a safe owned reference token.
- General Fortran value interfaces for FP8/FP6/FP4, complex, bitfields, compounds/vlens/NC_STRING and recursive ownership; future binding expansion beyond v4.3.0. Standard metadata smoke coverage here does not claim those interfaces.
- `varm`/`map`, F77 wrappers, half attribute wrappers, custom Fortran real kinds and new rounding/conversion engines: future binding expansion, not implicit work for Sprint 2.
- Fortran sanitizer-stack expansion: future CI work. Existing C ASan/UBSan/leak coverage remains mandatory.
- New filters/plugins, plugin discovery paths, chunking/quantization changes, backend format/layout changes, parallel/SWMR/in-memory support and unrelated defects: existing backlog/beyond v4.3.0.
- Conda recipe/feedstock changes: not needed because NEXTCDF-4 is disabled; publication remains Sprint 2.
- Release notes, tag, Spack release hash/version and upstream PR publication: Sprint 2. No implementation, commit or push is part of this refinement.
