# V3.0.1 Sprint 2: Conda

## Sprint Goal

Update the NEP Conda recipe to package the current v3.0.0 release as a minimal, reliable LZ4 compression distribution with Fortran wrappers, validate the built artifact end to end, and submit it to conda-forge through staged-recipes.

---

## Scope

**In scope:**
- Update `conda/meta.yaml` from v2.7.1 to v3.0.0 using the published v3.0.0 source tarball and its verified SHA256 checksum.
- Retain LZ4 compression and Fortran wrapper support; disable BZIP2 because no BZIP2 HDF5 plugin is available without changing NEP's local build behavior.
- Disable every UDF reader: CDF, GeoTIFF, GRIB2, FITS, PDS4, and DICOM.
- Remove reader-only dependencies, including `libdicom` and `libjpeg-turbo`.
- Simplify `conda/build.sh` so its recipe-only CMake invocation selects the existing LZ4 and Fortran options, disables BZIP2 and all readers, and omits reader-specific diagnostics and CMake debug-find output.
- Require the recipe's test section to verify the installed LZ4 HDF5 filter plugin on each supported platform and verify the installed Fortran module.
- Update Conda CI to render/lint the recipe, build it without upload, assert that a package is produced, and install that artifact in a clean Conda environment for a smoke test.
- Prepare the upstream staged-recipes contribution in conda-forge format and open a PR for the initial `nep` feedstock.
- Update user-facing installation and release-status documentation to identify the minimal v3.0.0 Conda package and its intentionally limited feature set.

**Out of scope:**
- Enabling or publishing any UDF reader in the Conda package.
- Changes to NEP runtime code, public APIs, CMake files or defaults, Autotools files or defaults, or local source-build behavior.
- Publishing a new NEP source release; the package targets the existing v3.0.0 tag.
- Adding Conda build variants for optional readers.

## Clarified Decisions

- The first conda-forge package release uses the existing NEP v3.0.0 source release.
- The upstream submission goes through `conda-forge/staged-recipes`; the generated `nep-feedstock` becomes the ongoing maintenance repository after acceptance.
- The package enables LZ4 and Fortran compression wrappers only. BZIP2 is disabled because NEP does not build or install its HDF5 plugin; every format reader, including DICOM, is also disabled.
- The minimal package retains core HDF5, NetCDF-C, NetCDF-Fortran, and LZ4 dependencies; no BZIP2 or format-library dependency is included. These choices apply only to the Conda recipe.
- Validation includes recipe render/lint, package build, installed-artifact checks, and a clean-environment install smoke test.
- Future Conda updates may introduce reader functionality after the minimal package is established.

## Major Tasks

### 1. Modernize the In-Repository Recipe

- Set the recipe version to `3.0.0` and replace the local source path with the immutable v3.0.0 GitHub tag tarball and verified checksum.
- Retain required compiler, CMake, HDF5, NetCDF-C, NetCDF-Fortran, LZ4, and BZIP2 dependencies.
- Remove `libdicom`, `libjpeg-turbo`, and all other format-reader dependencies.
- Keep package metadata and maintainer information aligned with conda-forge conventions.
- Add test commands for the `libh5lz4` plugin artifact on Linux and macOS, plus an installed Fortran module check.

### 2. Simplify the Build Script

- Pass the existing LZ4 and Fortran CMake options from the Conda build script and explicitly disable BZIP2.
- Pass existing reader-disable options from the Conda build script for CDF, GeoTIFF, GRIB2, FITS, PDS4, and DICOM.
- Remove reader-specific library/header probes and CMake debug-find logging from the Conda build script.
- Do not modify any NEP CMake source file, CMake default, Autotools file, or local build path.
- Build, test without masking failures, and install the package.

### 3. Strengthen Conda CI

- Render and lint the in-repository recipe before the package build.
- Build with `--no-anaconda-upload` and fail immediately on build or test errors.
- Resolve the generated package path and assert that the artifact exists.
- Create a clean environment, install the built artifact with its dependencies, and run a smoke test that verifies the installed LZ4 plugin.
- Preserve build logs on failure.

### 4. Submit to conda-forge

- Copy the finalized recipe into the `recipes/nep/` layout required by `conda-forge/staged-recipes`.
- Adjust only fields required by staged-recipes validation; keep the feature set identical to the in-repository recipe.
- Open the initial staged-recipes pull request and address automated and maintainer review feedback.
- After merge, confirm the generated `nep-feedstock` builds and that the package is installable from conda-forge.

### 5. Update Documentation

- Update `README.md` with the v3.0.0 Conda installation command and state that the first package contains LZ4 compression and Fortran wrappers only.
- Update `docs/prd.md`, `docs/prfaq.md`, and the applicable release-status documentation to distinguish the minimal Conda package from source builds with optional readers.
- Update `docs/roadmap.md` with the detailed-plan reference and sprint issue link.

## Acceptance Criteria

- [ ] `conda/meta.yaml` packages `nep` v3.0.0 from the verified immutable tag tarball.
- [ ] The recipe contains no DICOM or other format-reader dependency.
- [ ] `conda/build.sh` enables LZ4 and Fortran, disables BZIP2, and disables CDF, GeoTIFF, GRIB2, FITS, PDS4, and DICOM.
- [ ] The built package contains the LZ4 HDF5 filter plugin and the Fortran module.
- [ ] Recipe render/lint, build, and test commands pass without ignored failures.
- [ ] CI installs the built artifact into a clean Conda environment and completes its plugin smoke test.
- [ ] A conda-forge staged-recipes PR is opened for the minimal v3.0.0 package and passes its required checks.
- [ ] Documentation accurately describes the minimal Conda feature set and future reader-expansion path.

## Testing Requirements

- Run `conda render conda/` and the appropriate `conda-build` recipe validation command.
- Run `conda build conda/ --no-anaconda-upload` and require all build-phase CTest results to pass.
- Inspect the built artifact for the LZ4 plugin library and the Fortran module.
- In a clean environment, install the locally built artifact and verify the LZ4 plugin is present and loadable by the installed HDF5/NetCDF stack.
- Confirm the Conda CI workflow passes.
- Confirm staged-recipes validation and, after merge, the feedstock build pass.
