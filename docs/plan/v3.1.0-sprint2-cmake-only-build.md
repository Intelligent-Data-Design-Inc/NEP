# v3.1.0 Sprint 2: CMake-Only Build Migration

## Sprint Goal

Make CMake the sole supported NEP build system for v3.1.0. Remove the complete Autotools implementation and generated artifacts, preserve all supported configuration coverage through CMake and CTest, and update active user, package, and CI guidance accordingly.

## Scope

### In Scope

- Complete deletion of root and nested Autotools source inputs, generated files, macros, helper scripts, and Autotools-only test runners.
- CMake-only conversion of every active GitHub Actions workflow.
- Preservation of the current CMake configuration coverage for compression, optional readers, Fortran, examples, visualization, parallel I/O, documentation, Conda, and Spack where applicable.
- Updates to active user-facing build, install, test, package, Doxygen, design, product-requirement, FAQ, and release documentation.
- Clean CMake configure/build/CTest and documentation validation for the retained CI configurations.

### Out of Scope

- Raising the CMake minimum version; CMake 3.9 remains the declared minimum for this sprint.
- Changes to public CMake options, installation layout, format-reader behavior, compression filters, source APIs, or test-data content.
- A `./configure` compatibility wrapper, a legacy Autotools directory, or an alternate build system.
- Editing frozen historical roadmaps, plans, issues, release notes, or background material merely because they record the retired build system.

## Background

NEP presently supports equivalent CMake and Autotools paths. The root CMake build owns dependency discovery, generated configuration, CTest registration, HDF5 plugin builds, UDF `.ncrc` assembly, package configuration, documentation, and examples. Autotools has parallel authored and generated infrastructure distributed through the repository, including 25 `Makefile.am` files, 24 `Makefile.in` files, root and HDF5-plugin `configure`/`configure.ac` pairs, macro directories, generated helper scripts, and test runners. Seven active CI workflows contain Autotools jobs or steps: `ci.yml`, `ci-dicom.yml`, `ci-fits.yml`, `ci-formats.yml`, `ci-parallel.yml`, `ci-viz.yml`, and `geotiff-test.yml`.

The migration must delete unsupported paths rather than leave stale files that imply compatibility. The CMake build must remain behaviorally compatible for all currently supported feature selections.

## Major Tasks (Dependency Order)

1. **Inventory and classify Autotools-only files**
   - Create a deletion manifest before changing files.
   - Include root and nested `Makefile.am`/`Makefile.in`, `configure`/`configure.ac`, `aclocal.m4`, `config.h.in`, `autogen.sh`, `m4/` directories, Libtool helper files, generated dependency helpers, and Autotools-only test runners.
   - Retain source files, test data, public headers, CMake files, CMake templates, and runtime assets still used by CMake.
   - Verify that the `hdf5_plugins/` tree retains its CMake build definition and LZ4 plugin source while its Autotools material is removed.

2. **Remove Autotools implementation and generated artifacts**
   - Delete every item in the approved manifest, including root and nested build metadata.
   - Remove Autotools-only generated configuration templates and test scripts only where CMake has a direct replacement.
   - Update `.gitignore`, distribution/source-manifest references, and project tooling references that name deleted files.
   - Confirm a tracked-file search returns no Autotools inputs, generated artifacts, macros, or helper scripts.

3. **Audit and preserve CMake build functionality**
   - Verify each previously dual-built library, executable, test, plugin, `.ncrc` artifact, install rule, and documentation target is represented by CMake.
   - Correct CMake-only gaps exposed by removing files that were formerly shared indirectly with Autotools.
   - Keep CMake 3.9 compatibility and existing `NEP_*` public options unchanged.
   - Retain CTest as the sole local automated-test entry point.

4. **Convert all CI to CMake-only**
   - Remove Autotools build-system matrix values and conditional steps from `ci.yml`.
   - Convert or remove Autotools bootstrap, `autoreconf`, `./configure`, `make`, `make check`, Autotools-only environment variables, and Autotools-specific log collection in all focused workflows.
   - Preserve equivalent CMake configure, build, CTest, install, documentation, visualization, DICOM, FITS, format-reader, GeoTIFF, and MPI/parallel coverage.
   - Keep Conda and Spack workflows CMake-based and remove only stale Autotools terminology or assumptions.
   - Ensure workflow names, matrices, job summaries, and failure diagnostics accurately identify CMake.

5. **Update active documentation and package guidance**
   - Replace current CMake-or-Autotools build/test/install instructions in `README.md` with CMake-only equivalents.
   - Update active `docs/design.md`, `docs/prd.md`, `docs/prfaq.md`, `docs/Doxyfile.in`, format documentation, example documentation, and package guidance to remove live Autotools commands/options.
   - Add a v3.1.0 release note documenting the intentional removal and migration path to CMake commands.
   - Preserve historical documents that accurately record Autotools support at the time of their release.

6. **Validate the CMake-only repository**
   - Use clean build directories for default, minimal, compression-selection, Fortran on/off, reader-enabled, DICOM-enabled, examples, visualization, parallel-I/O, and documentation configurations applicable to the local environment and CI matrix.
   - Run CTest for each applicable configuration and build Doxygen with warnings treated as failures.
   - Verify installation and package-consumer checks retained by CI.
   - Search tracked files and active documentation/CI for `Autotools`, `autoreconf`, `autogen.sh`, `./configure`, `Makefile.am`, `Makefile.in`, and `make check`; allow intentional historical records only.

## Acceptance Criteria

- No root or nested Autotools input, generated artifact, macro, helper script, `Makefile.am`, `Makefile.in`, or Autotools-only test runner remains in the repository.
- The `hdf5_plugins/` CMake build and plugin sources remain available after its Autotools files are deleted.
- All active GitHub Actions workflows are CMake-only and contain no Autotools job, matrix value, bootstrap, configure, build, or test step.
- Retained CI configurations cover default/minimal/compression selections, Fortran on/off, enabled readers, DICOM, parallel I/O, visualization, documentation, Conda, and Spack as applicable.
- CMake configuration, build, CTest, install, and package-consumer behavior stays compatible with the supported v3.0.0 feature set.
- `README.md`, active documentation, Doxygen guidance, and packaging guidance provide CMake-only instructions and no active Autotools options or commands.
- Historical records are not rewritten solely to erase earlier Autotools support.
- A tracked-file and active-documentation/CI search finds no unsupported Autotools artifacts or references.

## Testing Requirements

- Clean CMake configure/build/CTest run for the default configuration.
- Clean CMake minimal configuration with optional readers, examples, and optional compression disabled as used in CI.
- CMake DICOM configuration with CTest regression coverage.
- CMake reader-format configurations covered by focused CI workflows.
- CMake Fortran-enabled and Fortran-disabled configurations.
- CMake parallel-I/O configuration under the supported MPI launcher.
- CMake visualization configuration with artifact validation.
- CMake documentation build with no Doxygen warnings.
- CMake install/package-consumer validation retained in CI.
- Repository search verifying deleted Autotools file classes and active references are absent.

## Build System and CI Integration

- Root and nested `CMakeLists.txt` files remain the sole build definitions.
- CMake-generated `config.h`, CTest registration, install rules, `.ncrc` generation, HDF5 plugin build, examples, Fortran targets, and documentation target remain supported.
- Update every workflow in `.github/workflows/` that has an Autotools-specific branch or wording.
- Keep Conda's existing CMake invocation and Spack's CMake package implementation.

## Dependencies and Risks

- **Dependency:** v3.1.0 Sprint 1 DICOM visualization work must be integrated or rebased so its CMake wiring is preserved while its Autotools wiring is removed.
- **Risk:** Nested `Makefile.in` files may be generated and tracked; the deletion manifest must distinguish them from source and CMake files.
- **Risk:** Focused CI workflows may have CMake and Autotools coverage that diverged. Each retained CMake job must preserve the intended feature test before removing its counterpart.
- **Risk:** Active documentation has widespread historical references. The implementation must limit edits to current instructions and avoid modifying frozen records.
- **Risk:** Local validation builds must use the repository `build` directory convention and begin from a clean build directory.

## Definition of Done

- CMake is NEP's only supported build system.
- All Autotools files and artifacts are deleted without removing CMake-required source or assets.
- All active CI workflows retain their intended coverage through CMake only.
- CMake configurations and tests required by the retained CI matrix pass.
- Active user, package, and API documentation uses CMake-only instructions; historical documentation remains intact.
- The roadmap and GitHub sprint issue link to this detailed plan.
