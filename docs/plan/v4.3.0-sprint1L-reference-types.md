# V4.3.0 Sprint 1L: Reference Types

Source: docs/roadmap.md, "V4.3.0 / Sprint 1L".

## Goal

Replace the deprecated HDF5 reference types with the current unified
reference model. `NC_REF_OBJECT`/`NC_REF_REGION` (backing
`H5T_STD_REF_OBJ`/`H5T_STD_REF_DSETREG`, both marked `\deprecated` in
HDF5 2.1.1) are removed from code, tests, and living documentation. In
their place, NEXTCDF-4 supports `H5T_STD_REF` — the single HDF5 2.x
reference datatype covering object, dataset-region, and attribute
references, including references to objects in other files — as a new
`nc_type` `NC_STD_REF`, plus a `libnep`-visible helper API for creating,
dereferencing, and inspecting reference tokens.

## Decisions

| Topic | Decision |
|-------|----------|
| API surface | Full helper API (Ed, 1b): `nc_std_ref_t` token typedef plus create/deref functions for object, region, and attribute references, including external-file creation. |
| Type constant | `NC_STD_REF` = 30 (Ed, 2a; revised from 32 — 32 collides with NC_FIRSTUSERTYPEID). `NC_REF_OBJECT` (30) and `NC_REF_REGION` (31) are removed entirely, not redefined. |
| Attributes | `NC_STD_REF` allowed on attributes (Ed, 3a) — the attribute path already routes through `NEXTCDF4_map_hdf_type`/`map_nc_type`. `nc_ref_attr`/`nc_deref_attr` take `obj_type`/`objid` so attribute references work on every object kind HDF5 supports: variables, groups, and committed datatypes (Ed, follow-up). |
| Historical docs | Update living docs only (Ed, 4a): `docs/nextcdf4.md`, `docs/design.md`, `docs/prd.md`, `docs/prfaq.md`, `docs/plan/NEXTCDF4_plan.md`, and the `hdf5`/`nextcdf4` skills. `docs/roadmap_v3.md` and `docs/releases/v4.0.0.md` stay as history; the removal is flagged in the v4.3.0 release notes (Sprint 2). |
| Restrictions | Keep both (Ed, 5a): no coordinate variables, no compound members. |
| Deref of external refs | `nc_deref_*` return `NC_ENOTNC4` for tokens pointing into another file; `nc_ref_get_file_name`/`nc_ref_get_obj_name` plus `nc_open` (or raw `H5Ropen_*`) are the resolution path. |

### 1. `include/nep.h` — constants, token type, and API

Remove `NC_REF_OBJECT`/`NC_REF_REGION` and their comments. Add, with
full Doxygen blocks in the existing `nc_*_bfloat16` style
(`@param`/`@return`, `@author Edward Hartnett, Intelligent Data
Design, Inc.`):

```c
/** NEXTCDF-4 HDF5 standard reference type (H5T_STD_REF). */
#define NC_STD_REF 30

/** Size in bytes of one opaque NC_STD_REF token (matches HDF5
 *  H5R_ref_t, H5R_REF_BUF_SIZE). */
#define NC_STD_REF_SIZE 64

/** One opaque NEXTCDF-4 reference token; layout-compatible with
 *  HDF5 H5R_ref_t. Do not interpret the bytes. */
typedef struct {
    union {
        unsigned char bytes[NC_STD_REF_SIZE];
        int64_t align;
    } u;
} nc_std_ref_t;

/* Token kinds returned by nc_ref_get_type(). */
#define NC_STD_REF_OBJECT 1  /**< object reference */
#define NC_STD_REF_REGION 2  /**< dataset region reference */
#define NC_STD_REF_ATTR   3  /**< attribute reference */

/* Object target kinds for nc_ref_object()/nc_deref_object(). */
#define NC_REF_OBJ_VAR  1  /**< NetCDF variable (HDF5 dataset) */
#define NC_REF_OBJ_GRP  2  /**< NetCDF group (HDF5 group) */
#define NC_REF_OBJ_TYPE 3  /**< NetCDF user-defined type (HDF5 committed datatype) */
```

### 2. `src/nextcdf4/nxt4ref.c` — new file in `ncnextcdf4`

Add `nxt4ref.c` to the `add_library(ncnextcdf4 ...)` source list in
`src/nextcdf4/CMakeLists.txt`. Doxygen file header per project
convention (`@file`, `@brief`, `@author Edward Hartnett`, `@date`,
`@copyright`). Follow `nxt4err.h` conventions: `int ret = NC_NOERR;`,
`EBAIL`/`EBAIL2`, `fail:` label, `ELOG((2|3, ...))`.

Common rules for all 13 functions:

- File-scope `_Static_assert(sizeof(nc_std_ref_t) == sizeof(H5R_ref_t), ...)`
  and cast `nc_std_ref_t *` ↔ `H5R_ref_t *` through `void *`.
- Resolve `ncid` with `nc4_find_grp_h5` + `NEXTCDF4_get_file`; a
  non-NEXTCDF4 `ncid` returns `NC_ENOTNC4`.
- Every `nc_ref_*` create function additionally requires native mode:
  `file->netcdf4_model || (file->mode & NC_CLASSIC_MODEL)` → `NC_ENOTNC4`.
  `nc_deref_*`/`nc_ref_get_*` work in any NEXTCDF4 mode.
- Token-kind check: `nc_deref_*` first verifies `H5Rget_type` (region
  for `nc_deref_region`, `H5R_ATTR` for `nc_deref_attr`; `nc_deref_object`
  accepts `H5R_OBJECT`) and returns `NC_EINVAL` on mismatch.
- External detection: helper `nx4_ref_is_external(file, ref)` calls
  `H5Rget_file_name` (two-call pattern: query length, then fetch) and
  compares with `H5Fget_name(file->hdfid)`; external → `NC_ENOTNC4`
  from all three `nc_deref_*`.
- `H5Ropen_*` failure (dangling/deleted target) → `NC_EINVAL`.
- Internal helper `nx4_obj_ids(h5, hid_t obj, int *obj_typep,
  int *grpidp, int *idp)`: `H5Iget_type(obj)` maps
  `H5I_DATASET`→`NC_REF_OBJ_VAR`, `H5I_GROUP`→`NC_REF_OBJ_GRP`,
  `H5I_DATATYPE`→`NC_REF_OBJ_TYPE` (else `NC_EINVAL`); then
  `H5Iget_name(obj)` gives the absolute path; walk the
  `NC_GRP_INFO_T` tree by path components (a static
  `nx4_grp_for_path` helper over `grp->children`) to get `grpid`;
  basename lookup in `grp->vars` → `varid`, `grp->type` list →
  `typeid`, or the group itself → `idp == grpid`. Do this on the
  `NC_*_INFO_T` lists directly — no reentry into public `nc_*` calls.

Function behavior:

- `nc_ref_object`: `obj_type` selects the handle — `NC_REF_OBJ_VAR` →
  `nc4_find_grp_h5_var` → `vinfo->hdf_dataset`; `NC_REF_OBJ_GRP` →
  `ginfo->hdf_group` for that `ncid`; `NC_REF_OBJ_TYPE` →
  `tinfo->hdf_type`. Get the object name via `H5Iget_name`, then
  `H5Rcreate_object(file->hdfid, name, H5P_DEFAULT, (H5R_ref_t *)ref)`.
- `nc_deref_object`: `H5Ropen_object` → `nx4_obj_ids`.
- `nc_ref_region`: `nc4_find_grp_h5_var` → `H5Dget_space(vinfo->hdf_dataset)`
  → `H5Sselect_hyperslab` with `start`/`count`/`stride` converted to
  `hsize_t` (NULL `stride` = all 1; reject stride < 1) →
  `H5Rcreate_region(file->hdfid, name, space, H5P_DEFAULT, ref)`.
- `nc_deref_region`: `H5Ropen_region` returns the region dataspace;
  require `H5Sis_regular_hyperslab` else `NC_EINVAL`;
  `H5Sget_regular_hyperslab` yields start/stride/count/block — require
  block == 1 in every dimension else `NC_EINVAL`; report `ndimsp`,
  `start`, `count`, `stride` (NULL-tolerant); `varid`/`grpid` via
  `H5Ropen_object` + `nx4_obj_ids`.
- `nc_ref_attr`: `obj_type` dispatches exactly like `nc_ref_object` —
  `NC_REF_OBJ_VAR` → attribute on the variable's dataset,
  `NC_REF_OBJ_GRP` → attribute on that group (what the NetCDF API
  calls a global attribute on `NC_GLOBAL`), `NC_REF_OBJ_TYPE` → an
  HDF5 attribute on the committed datatype. Every object kind HDF5
  attributes can attach to is covered; note that NetCDF has no
  `nc_put_att` for types, so a datatype attribute can only exist if
  created through raw HDF5 — the reference API must still be able to
  point at it. Verify the attribute exists with `H5Aexists` on the
  resolved owner handle; then `H5Rcreate_attr(file->hdfid, owner_path,
  att_name, H5P_DEFAULT, ref)` with `owner_path` from `H5Iget_name`.
- `nc_deref_attr`: `H5Ropen_object` on the token → `nx4_obj_ids` for the
  owner, so `*obj_typep` reports `NC_REF_OBJ_VAR`/`NC_REF_OBJ_GRP`/
  `NC_REF_OBJ_TYPE` for all attribute-bearing object kinds;
  `H5Ropen_attr` → `H5Aget_name` into `att_name` (caller buffer
  must hold `NC_MAX_NAME + 1`).
- `nc_ref_object_ext`/`nc_ref_region_ext`/`nc_ref_attr_ext`: `ncid` is
  validated like `nc_ref_object` (destination must be a native-mode
  NEXTCDF4 file); then `H5Fopen(filename, H5F_ACC_RDONLY, H5P_DEFAULT)`,
  create the ref against that file with `path` as the HDF5 object name
  (region variant: `H5Dopen2` → `H5Dget_space` → select hyperslab →
  `H5Rcreate_region`; attr variant: `H5Rcreate_attr` — `path` may name
  any attribute-bearing object kind, so `nc_ref_attr_ext` covers the
  same owner set as `nc_ref_attr`), `H5Fclose`. The
  resulting token encodes `filename` and resolves cross-file.
- `nc_ref_get_type`: `H5Rget_type` → `NC_STD_REF_OBJECT`/`REGION`/`ATTR`.
- `nc_ref_get_file_name`/`nc_ref_get_obj_name`: wrap
  `H5Rget_file_name`/`H5Rget_obj_name`; query the needed length first,
  `NC_EINVAL` if `name`/`size` can't hold it.

## Implementation notes (added during the sprint)

- `NC_STD_REF` = **30**, not 32: netcdf-c assigns user-defined typeids
  from `NC_FIRSTUSERTYPEID` = 32, so 32 would collide with the first
  committed type in every file.
- `H5Rcreate_*` produce `H5R_OBJECT2`/`H5R_DATASET_REGION2` token kinds,
  while the `H5R_OBJECT`/`H5R_DATASET_REGION` macros alias the legacy
  `*1` values — kind checks accept both `*1` and `*2`.
- A `H5R_ref_t` token holds an open reference to its file: `nc_close`
  defers the underlying `H5Fclose` while tokens are live, and a raw
  `H5Fopen` on the same file then fails with "file close degree doesn't
  match" (NEXTCDF-4 uses `H5F_CLOSE_STRONG`). `nc_ref_free()` was added
  to the API for this reason.
- Tokens read back from disk are byte-different from live tokens
  (transient state inside the 64-byte struct); tests verify them by
  dereference, not `memcmp`.
- `NEXTCDF4_inq_att` replaced stock `NC4_inq_att` in the dispatch table:
  the stock version resolves `att->nc_typeid` via `nc4_find_type`, which
  rejects every NEP atomic typeid and broke `nc_inq_att` and generic
  `nc_get_att` for all NEP-type attributes (float16 included). Now the
  stored typeid is returned directly.
- `nc_put_att` requires define mode *and* the target dataset to exist —
  variable attributes are written in `nc_redef` after the first
  `nc_enddef`.
- An irregular region needs unequal hyperslab blocks: a union of
  single-point slabs coalesces to a regular selection in HDF5.
