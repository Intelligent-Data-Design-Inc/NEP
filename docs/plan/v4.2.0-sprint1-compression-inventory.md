# v4.2.0 Sprint 1: Compression Inventory and Compatibility Contract

**Handoff:** [Sprint 1 results](v4.2.0-sprint1-results.md) record the inventory, API/package decisions, local plugin probe, and remaining gates.

## Goal

Define the boundary between NEP and `/fast/ed/nep-compress/` before moving any code. Produce a checked inventory, a migration contract for existing C/Fortran users and HDF5 files, and a decision on BZIP2 plugin provisioning. This sprint is planning and baseline verification only; implementation, publishing, and removal belong to Sprints 2-4 in [the roadmap](../roadmap.md).

NEP continues to own UDF format readers, NEXTCDF-4, logging, and their public interfaces. nep-compress will own the compression APIs and their runtime plugin requirements, with no dependency on NEP logging. Keep the published filter IDs and API signatures, but old-NEP/new-project file interchange is not a migration gate. Moving the API to a different package requires an explicit source/build migration, not an undocumented promise of drop-in linking.

## Scope and Baseline

Use the checked-in code and CMake configuration as the source of truth when documentation disagrees. In particular, `CMakeLists.txt` currently defaults `NEP_BUILD_LZ4=ON` and `NEP_BUILD_BZIP2=OFF`; some active documentation and the Spack recipe claim BZIP2 defaults ON or that NEP builds its plugin. The root CMake builds `libh5lz4` from `hdf5_plugins/LZ4/src/H5Zlz4.c`, but there is no BZIP2 plugin source in NEP. Resolve these contradictions in the migration contract instead of carrying them into nep-compress.

For each item, record its destination (move, retain, update, or retire), reason, consumers, and test or doc that verifies the decision. Search for indirect references as well as filenames: `NEP_BUILD_LZ4`, `NEP_BUILD_BZIP2`, `BUILD_LZ4`, `BUILD_BZIP2`, `NEP_HAS_LZ4`, `NEP_HAS_BZIP2`, `HDF5_PLUGIN_PATH`, `nc_def_var_*`, `nf90_*`, `nepf`, `nep.mod`, and plugin install paths. Do not treat hits in old release notes as live build dependencies.

**Logging boundary:** Do not move `include/nep_logging.h`, `nep_log()`, `nep_set_log_level()`, or the `NEP_ENABLE_LOGGING` build option to nep-compress. The active LZ4/BZIP2 routines in `src/nep.c` currently have no `ELOG` calls; the NEP logging implementation is in the same file but outside those routines. If logging statements are encountered in compression code during extraction, comment them out for now and leave normal error returns and plugin-availability checks intact. Do not introduce a logging dependency or replace diagnostic calls with new infrastructure in this migration.

## Compatibility Contract to Record

1. **Disk format:** Retain `LZ4_ID=32004` and `BZIP2_ID=307` and the one-parameter API. Test nep-compress's own write/reopen/read round trips, values and filter metadata. Do not require files written through old NEP to be read through nep-compress, or the reverse.
2. **C source and behavior:** Keep `nc_def_var_lz4`, `nc_inq_var_lz4`, `nc_def_var_bzip2`, and `nc_inq_var_bzip2` signatures and error semantics (levels 1-9, `NC_EINVAL` for invalid levels, `NC_EFILTER` when a required plugin is unavailable, and filter inquiry semantics). Specify the new installed header and library names before implementation; document the required changes from `<nep.h>` and `-lnep` rather than claiming binary ABI compatibility across packages. Verify any non-compression declarations in `nep.h` remain available to NEP users.
3. **Fortran source and linkage:** Keep the four `nf90_*` procedure names and 1-based Fortran variable-ID conversion. Decide and document the replacement for `use nep` and `-lnepf`, including the `nep.mod` filename and module search path. Do not install a second `nep.mod` alongside NEP's existing module in the same prefix.
4. **Plugin discovery:** Record `libh5lz4` as the currently built plugin, its `${CMAKE_INSTALL_LIBDIR}/plugin` install location, and the test-tree plugin directory. Determine the actual external BZIP2 plugin name/path and test whether `H5Zfilter_avail(307)` succeeds. Distinguish a plugin needed to *write* from one needed to *read* existing compressed data; verify both operations with the specified `HDF5_PLUGIN_PATH`.
5. **Build/packaging:** Record actual CMake defaults and dependencies, test registration, the effect of disabling each filter, generated `NEP_HAS_*` macros, and downstream CMake/Spack/Conda assumptions. Choose nep-compress's option names/defaults explicitly; plan a clear diagnostic or migration note for removed NEP options. Audit NEXTCDF-4's use of generic NetCDF/HDF5 filters so extraction does not disable that backend's filter support.
6. **Logging independence:** Confirm the extracted code builds and links without `nep_logging.h`, `nep_log`, `nep_set_log_level`, or `NEP_LOGGING`. NEP retains its logging behavior and NEXTCDF-4 logging tests. Commented-out compression logging must not change return codes or mask failures.

These are compatibility requirements, not claims that all cases already pass. Capture baseline observations and known exceptions separately from decisions.

## BZIP2 Provisioning Decision

Before Sprint 2, choose and write down **one** supported model:

- Bundle/build a properly licensed BZIP2 HDF5 plugin in nep-compress (source and provenance must be established; NEP does not currently supply it), or
- Depend on an existing compatible HDF5 BZIP2 plugin, with explicit discovery, a failure message when enabled but missing, and documentation and CI that install/test it.

Whichever model is chosen must support nep-compress's create/reopen path for filter ID 307; `libbz2` alone is not proof that the HDF5 plugin is available. If a plugin cannot be sourced or detected, mark BZIP2 support blocked rather than silently calling the standalone project complete.

## Work Sequence

1. Freeze the Sprint 1 baseline: record NEP and nep-compress revisions, enabled CMake options, available local dependency versions, and pre-existing test failures. Work from a clean `build` directory when running a new build; do not delete an existing build without checking whether it contains user data.
2. Fill out the inventory table above with exact symbols, targets, install paths, tests, docs, CI, and package references. Check actual consumers of `nep`/`nepf` and NEXTCDF-4 before marking a shared file for removal.
3. Write a short migration checklist with old -> new header, library, Fortran module, CMake option, and `HDF5_PLUGIN_PATH` entries. For undecided new names, write "TBD" and assign the decision before Sprint 2 rather than inventing a public name.
4. Resolve BZIP2 provisioning and verify plugin availability on the three local installations. Record plugin origin, licensing, environment setup, and how CI can reproduce the test.
5. Specify verification commands for nep-compress LZ4 and BZIP2 write/reopen/read tests, including filter IDs and parameters; no cross-project fixtures are required.
6. Review current docs, packaging, and CI contradictions; hand Sprints 2-4 a list of edits ordered by dependency. Leave historical releases as historical, repairing broken links rather than rewriting what shipped.

## Deliverables and Exit Gate

- A completed move/retain/update/retire inventory with ownership and downstream consumers for every area above.
- A migration checklist and compatibility matrix for C, Fortran, file format, plugin discovery, build flags, and mixed NEP/nep-compress installations.
- A recorded BZIP2 provider decision, plugin provenance and licensing check, and reproducible test procedure (or an explicit blocker).
- A baseline test report and a list of current documentation/build discrepancies, including BZIP2 defaults and the missing bundled plugin.
- Sprint 2 may begin only after the API/module ownership, plugin provider, logging boundary, and independent round-trip tests are specified. No compression code is removed from NEP in Sprint 1.
