# v4.3.0 Sprint 1N2: Nested Types and Array Fields

Source: docs/roadmap.md, "V4.3.0 / Sprint 1N2".

## Goal

Fixed-size user types compose reliably: compounds contain other fixed-size compounds, enums, opaque fields, and multidimensional array fields. Definitions, values, and complete field metadata survive reopen and upstream NetCDF-4 interchange in native and compatibility modes, without changing native complex storage or the documented reference restriction.

## Decisions

| Topic | Decision |
|-------|----------|
| Prerequisite | Finish 1N1 first; reuse its context-aware type helpers and staged persistence rather than invent another resolver. |
| Modes | Native and `NC_NETCDF4_MODEL`, with recursive compatibility checks (Ed, 1a). |
| Scope | Fixed-size composition now; all non-string variable-length nesting in 1N3 (Ed, 2a). |
| Tests | Focused array/nesting tests here; upstream ports in 1N4 (Ed, 3b). |
| CI | Existing NEXTCDF-4 job automatically runs the enabled tests; dedicated sanitizer job arrives in 1N3 (Ed, 4b). |
| Surface | Implement existing `nc_insert_array_compound`; no new installed API or CMake option. |
| Unsupported members | Reject `NC_STD_REF` recursively, including through an array; dynamic types wait for 1N3 and strings for 1P. |

## Work items

### 1. One insertion path for scalar and array fields

Files: `src/nextcdf4/nxt4type.c`, `nxt4internal.h`.

Keep the existing public dispatch signatures. Implement `NEXTCDF4_insert_array_compound`; route `NEXTCDF4_insert_compound` through it with `ndims=0`, `dim_sizesp=NULL`. Resolve the container and member type using 1N1's `nx4_find_type`/`nx4_type_size`/`nx4_file_type` helpers. Reject missing/invalid compound ids, read-only files, classic mode, committed-type mutation and invalid names before mutating either HDF5 or metadata. Rank zero is scalar. For positive rank, require a non-NULL size vector, positive dimensions, and valid rank; guard dimension products and `offset + product * member_size` against overflow and the compound size. Reject duplicate field names, direct/indirect type cycles, and forbidden reference members. Match upstream valid-layout behavior rather than adding an undocumented padding/overlap restriction.

Create the array member using `H5Tarray_create2` over the resolved base type, insert with `H5Tinsert`, and add `nc4_field_list_add` metadata including rank/dimensions. Retain C ordering for dimension sizes. Close temporary member/array handles on every exit. Validate before insertion so a failed call does not leave a field only in HDF5 or only in the metadata list. Rebuild the transient compound from validated metadata if needed to keep updates atomic; never attempt to edit a committed datatype.

### 2. Dependency ordering and recursive native layouts

Files: `nxt4type.c`, `nxt4meta.c`, `nxt4internal.h`, `nxt4io.c`.

Extend 1N1 helpers for nested fixed-size members. Recursively resolve member file datatypes and memory datatypes; preserve explicit C offsets/padding on definitions and report the chosen native layout consistently on reopen. Do not copy file-endian records blindly into host structs. Carry array rank/shape and nested member typeids through inquiry. Commit dependency types before containers; freeze dependencies consistently when a container is committed. Reject a cycle with `NC_EBADTYPE`, with no partially committed container.

The load path registers named identities first, then resolves their members/dependencies, independent of HDF5 link iteration order. For an array member, unwrap `H5T_ARRAY`, recover rank/extents, resolve its base through the same committed-object resolver, then populate the field record. Distinct named types with equal structures stay distinct. No `{r,i}` complex recognition is added.

Recursively enforce `NC_NETCDF4_MODEL`: standard enhanced-model compositions are accepted; a NEP-specific atomic anywhere in the graph is rejected. Native mode permits supported fixed-size NEP atomics as members except `NC_STD_REF`; no numeric conversion API is added. Vlen/string-containing compositions must fail explicitly until their owning sprint, not take a shallow-copy fixed-size path. Cover type equality via `NEXTCDF4_inq_type_equal` structurally (class, bases, member names/types/shapes/layout), not by file-local numeric id or type name alone.

### 3. Enabled array/nesting regression test

Files: new `test/nextcdf4/tst_nextcdf4_compound_arrays.c`, `test/nextcdf4/CMakeLists.txt`, extend `tst_nextcdf4_user_types.c` where shared behavior needs pins.

Register `tst_nextcdf4_compound_arrays` with the existing NEXTCDF-4 test environment and libraries. Cover scalar nested compound, enum/opaque members, rank-1/rank-2 atomic arrays and arrays of compounds; use `offsetof` and real C structs with deliberate padding. Compare fields individually. Check each inquiry field, shape and offset before/after reopen, plus `nc_inq_type_equal` across independently created files. Include compound variables and attributes, hyperslab/strided I/O, inherited types, different same-name subgroup types, dependency names sorting after the container, and both interchange directions (upstream writer/NEXTCDF-4 reader and compatibility writer/upstream reader).

Negative tests cover rank, zero/negative extents, NULL vector, multiplication/offset overflow, invalid type, duplicate field, cycle, committed edit and reference-through-array/nesting rejection. A rejected insertion must leave the original field count and later valid I/O unchanged. Native-only member tests stay separate from standard compatibility fixtures. Dynamic nesting tests belong to 1N3.
