# V4.3.0 Sprint 1I: Better Documentation

Source: docs/roadmap.md, "V4.3.0 / Sprint 1I".

## Goal

`src/nextcdf4/` becomes genuinely readable documentation: every
function gets a structured walkthrough of what it does and why, every
non-obvious code block gets a "why" comment, and the Doxygen prose is
written for an end user who may not already know netCDF or NEXTCDF-4
concepts (dispatch tables, UDF slots, `_enddef`, dimension scales,
hidden attributes). A new architecture page ties the per-function docs
together so the concepts are explained once and `@ref`'d everywhere.
The public NEXTCDF-4 headers and the user-facing markdown pages get the
same end-user treatment where they are thin.

## Decisions

| Topic | Decision |
| --- | --- |
| File scope | `src/nextcdf4/*.c` (all 9 files, including `nxt4convert.c`), `nxt4internal.h`, `nxt4err.h`, **plus** public headers `include/nextcdf4dispatch.h` and the NEXTCDF-4 sections of `include/nep.h`, **plus** user-facing prose docs `docs/nextcdf4.md`, `docs/NEXTCDF4_float16.md`, `docs/mainpage.md`. (Ed: 1c) |
| Comment density | Every function gets a short `/*` walkthrough paragraph at the top of its body explaining the algorithm's steps; genuinely trivial bodies get one line. Plus targeted "why" comments on non-obvious statements — not a comment on every control-flow block. (Ed: 2a) |
| Internal-function docs | Same end-user treatment as public functions: each doc explains what the function does in the dispatch lifecycle with brief concept explanations, linking to the architecture page and `docs/nextcdf4.md` where relevant. No `@internal` marking. (Ed: 3a) |
| Architecture page | One new `docs/nextcdf4_architecture.md` `@page` added to `INPUT`; per-function docs `@ref` it instead of repeating concept explanations. (Ed: 4a) |

## Current state (2026-11-20)

- `src/nextcdf4/` has 11 files, 6469 lines. Sprint 1F converted every
  documentation block to `/**` with `@param`/`@return` —
  `grep -c '/\*\*'` counts: `nxt4meta.c` 64, `nxt4internal.h` 97,
  `nxt4type.c` 27, `nxt4file.c` 15, `nxt4group.c` 13, `nxt4convert.c`

## Work items

### 1. New architecture page `docs/nextcdf4_architecture.md`

Create the page, add it to `docs/Doxyfile.in` `INPUT` next to
`docs/nextcdf4.md` (line ~983), and give it a `@page
nextcdf4_architecture` anchor so code can `@ref` it.

Content, written for a reader who knows netCDF at the `nc_open`/
`nc_put_var` level but not internals — draw on
`.devin/skills/nextcdf4/SKILL.md` (verify every claim against the
code):

- What a UDF expansion pack is; slot `NC_UDF9`/`NC_NEXTCDF4`, explicit
  selection via `nc_create`/`nc_open`, `.ncrc` autoload. Describe the
  UDF mechanism only in terms of current netcdf-c `main`, which
  provides 64 UDF slots (UDF0–UDF63); do not mention the previous
  10-slot scheme.
- The dispatch table: what `NC_Dispatch` is, which calls NEXTCDF-4
  implements itself vs delegates to `NC4_*` shared helpers vs stubs
  (`NC_NOTNC4_*`, `NC_NOOP_*`, `NC_RO_set_fill`).
- Per-object state: `NEXTCDF4_FILE_INFO_T` and the `NC_*_INFO_T`
  format-private fields for group/dim/var/type (`nxt4internal.h`).
- Hidden marker attributes and dimension scales:
  `NEXTCDF4_BACKEND_ATT`, `NEXTCDF4_MODEL_ATT`, `NEXTCDF4_DIMID_ATT`,
  `NEXTCDF4_VARID_ATT`, `NEXTCDF4_VARDIMIDS_ATT`,
  `NEXTCDF4_DIMCLASS`; why they exist and why `is_reserved_att`
  filters them.
- Metadata lifecycle: define mode vs data mode, `NEXTCDF4_load_metadata`
  on open vs materialization at `_enddef`.
- Compatibility modes (`NC_CLASSIC_MODEL`, `NC_NETCDF4_MODEL`) and
  what each does to the superblock and allowed types.
- Error/logging conventions: `EBAIL`/`EBAIL2`, `fail:` labels,
  `ELOG` levels.
- Conversion engine: what `nxt4convert.c` does and when HDF5
  conversion is still used (IEEE float16 exception).

### 2. Deepen function documentation in `src/nextcdf4/*.c`

For each of the 9 `.c` files, expand every `/**` block from one-liner
to end-user prose:

- A `@brief` that says what the function does *in the lifecycle*
  ("called by netcdf-c's `nc_enddef` through the dispatch table to
  write all pending metadata to HDF5"), not just a restatement of the
  name.
- Prose explaining the relevant concept briefly where the reader
  needs it (e.g. `NEXTCDF4_map_hdf_type` explains what an `nc_type`
  is and that NEXTCDF-4 stores every atomic type as a committed copy
  of an HDF5 predefined type), with `@ref nextcdf4_architecture` or
  `@ref nextcdf4` for the long version.
- Keep all existing `@param`/`@return`/`@retval` entries; fix stale
  ones (Sprint 1F warned some blocks may not match their signature).
- Give skeleton blocks like `is_reserved_att` (`nxt4meta.c:43`) a
  real `@brief`.
- Do not reduce accuracy for accessibility — explain concepts in a
  sentence or two and `@ref`, don't paraphrase the algorithm in the
  doc block (that's work item 3's walkthrough comment).

Apply per file; `nxt4meta.c` (3324 lines, 64 blocks) is the bulk and
can be split across editing passes. `nxt4convert.c` is in scope — its
11 blocks document the conversion engine the architecture page
describes.

### 3. Walkthrough and "why" comments in bodies

In the same files, add plain `/*` comments:

- At the top of each function body (below declarations), a short
  paragraph describing the steps the body performs; one line for
  trivial bodies like `NEXTCDF4_check_write_define`.
- Targeted "why" comments on non-obvious statements: HDF5 idiom
  choices (scale attachment order, `H5Tcopy` ownership, datatype
  close), refcount/ownership rules for `NC_FILE_INFO_T` vs
  `NEXTCDF4_FILE_INFO_T`, format quirks (reserved atts, marker atts,
  dimid/varid encoding), deliberate deviations from netcdf-c's
  `libhdf5`, and the conversion-engine subtleties in `nxt4convert.c`
  (alias-safe bit access, 64-bit boundary avoidance, RNE rounding).
- No comments on self-evident statements.

### 4. Public headers

- `include/nextcdf4dispatch.h`: expand the one-line blocks —
  `NC_NEXTCDF4_create`/`open`/`abort`/`close`/`sync`/`inq`/
  `inq_format`/`inq_format_extended`, `NC_NEXTCDF4_initialize`/
  `finalize`, `NEXTCDF4_dispatcher` — to explain what each entry does
  for a user, that most callers use `nc_create`/`nc_open` rather than
  calling these directly, and where UDF slot 9 fits.
- `include/nep.h`: the NEXTCDF-4-visible parts — `NC_NEXTCDF4`
  (line ~290), the `nc_ref_object`/`nc_deref_object`/`nc_ref_region`
  declarations, and the `nc_*_bfloat16` family — get prose explaining
  bfloat16 as a storage type vs the C-side `nc_bfloat16_t`, raw-bit vs
  converting calls, and `@ref` links to `docs/NEXTCDF4_float16.md`.
  Keep the existing `@author Edward Hartnett, Intelligent Data
  Design, Inc.` lines.

### 5. User-facing prose docs

- `docs/nextcdf4.md`: add a short "How it works" section near the top
  summarizing the architecture page for end users (2-4 paragraphs +
  link), and review each existing section for the same end-user bar —
  explain terms at first use (UDF, dispatch, dimension scale).
- `docs/NEXTCDF4_float16.md`: same first-use-of-term pass; ensure the
  bfloat16 section matches the `nep.h` prose from work item 4.
- `docs/mainpage.md`: add a one-paragraph NEXTCDF-4 pointer to the
  architecture page if the main page doesn't already route readers
  there.

### 6. Consistency pass

- Every new `@ref`/`@see` target must exist (`nextcdf4_architecture`,
  `nextcdf4`, function names). Broken refs are warnings and fail the
  build.
- No `@author`/`@date` additions on function blocks beyond existing
  house style; new file keeps the standard
  `@file`/`@brief`/`@author Edward Hartnett`/`@date`/`@copyright
  Intelligent Data Design, Inc. All rights reserved.` header.
