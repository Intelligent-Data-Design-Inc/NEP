# v4.3.0 Sprint 1L1: Allow float16/bfloat16 Coord Vars

Source: docs/roadmap.md, "V4.3.0 / Sprint 1L1".

## Goal

Ratify in tests and documentation what the code already does: small
floating-point types (`NC_FLOAT16`, `NC_BFLOAT16`, and the FP8/FP6/FP4
family) may be used as coordinate variables in native NEXTCDF-4 mode,
resolving issue #380 by lifting the design ban rather than enforcing
it. The same ratify-don't-ban treatment is applied to `NC_STD_REF`
coordinate variables, whose documented ban is likewise unenforced.
One real defect found while verifying the ratification — the in-session
dimension-name staleness after renaming a coordinate variable — is
fixed so that inquiry results match post-reopen state.

## Decisions

| Topic | Decision |
|-------|----------|
| Policy on small-float coord vars | Allowed (ratify code behavior); ordering/comparison semantics of non-IEEE encodings are the caller's concern. Resolves #380. |
| Test coverage | `NC_FLOAT16` and `NC_BFLOAT16` only (Ed, 1c). FP8/FP6/FP4 are documented as allowed but not exercised in the committed test. |
| Test location | Extend `test/nextcdf4/tst_nextcdf4_var.c` (Ed, 2a); `test_coordinate` already lives there. No new CMake registration. |
| Rename in-session staleness | Fix in this sprint (Ed, 3a): detect the coordinate variable *before* updating `var->hdr.name` in `NEXTCDF4_rename_var`, and sync the in-memory variable name in `NEXTCDF4_rename_dim`. Regression checks added in-session. |
| `NC_STD_REF` coord vars | Allowed — remove the ban from the docs (Ed, 4). No `def_var` enforcement is added; verified define/reopen works. |
| Roadmap ban text | Mark superseded in both `docs/roadmap.md` (its own v4.0.0 Sprint 9 copy) and `docs/roadmap_v3.md` (Ed, 5a). |
| Interop caveat | Third-party tools (ncdump, CF checkers) may not understand small-float coordinate values; documented as an interop caveat, not a correctness issue. |

## Current state (2026-11-21)

Verified by reading the code and by a throwaway probe program linked
against `build/src/libncnextcdf4.so` (HDF5 2.1.1, netcdf-c
4.10.2-development, `NCRCENV_RC=build/.ncrc`):

- `NEXTCDF4_def_var` (`src/nextcdf4/nxt4meta.c:1084`) detects a
  coordinate variable by `ndims == 1 && !strcmp(name,
  var->dim[0]->hdr.name)` (line 1182), deletes the placeholder `int8`
  scale dataset created by `NEXTCDF4_def_dim` (line 975), and recreates
  it with the variable's datatype (lines 1208–1222). **No type check
  exists** — any atomic type `NEXTCDF4_check_atomic_type` accepts can
  be a coordinate variable today.
- Probe results (all `NC_NOERR` unless noted): fixed `NC_BFLOAT16`
  coord var defines, stores raw bits, reopens with `nc_inq_vartype ==
  NC_BFLOAT16`, bit-exact round-trip, typed `nc_get_var_float` reads,
  and a dependent `NC_INT` var resolves its dimid; unlimited
  `NC_FLOAT16` coord var appends, survives reopen, and appends again;
  `NC_FLOAT8_E4M3` coord var round-trips untyped; `NC_STD_REF` coord
  var defines and reopens with the right type. `NC_CLASSIC_MODEL` and
  `NC_NETCDF4_MODEL` reject the same definitions (`check_atomic_type`,
  `nxt4meta.c:371`).
- **Defect found**: `NEXTCDF4_rename_var` calls `coord_var_dim()`
  (`nxt4meta.c:2356`) *after* `var->hdr.name` is replaced
  (lines 2350–2351), so the name comparison can never match and the
  dim-rename block (lines 2357–2374) is dead code. In-session
  `nc_inq_dimname` returns the stale name; post-reopen state is
  correct because the loader uses the link name. Reproduced with
  `NC_INT` — the bug is not small-float specific. Mirror issue in
  `NEXTCDF4_rename_dim` (lines 2260–2263): the in-memory coordinate
  variable name is deliberately left stale.
- **Pre-existing edge (all types, out of scope)**: a variable defined
  in a subgroup whose name matches an ancestor group's dimension is
  misdetected as a coordinate variable; `H5Ldelete` on the wrong group
  fails `nc_def_var` with `NC_EHDFERR`.
- Loader (`nxt4meta.c:2655`–`2990`): `find_dim_cb` collects scales by
  `CLASS=DIMENSION_SCALE` + `_Netcdf4Dimid`; `find_var_cb` collects
  the same dataset as a variable via `_Netcdf4Varid`; `load_one_var`
  resolves the datatype through `map_nc_type` (covers every small
  float, line 607) and dimids via `_Netcdf4Coordinates` or the
  scale-iteration fallback (type-agnostic).
- `nx4_create_var_dataset` (`nxt4meta.c:1290`) — the def-var-setter
  recreation path — already special-cases coordinate variables;
  the stale-attachment hazard on dependent vars is #382 (Sprint 1M).
- Docs claiming the bans: `docs/plan/NEXTCDF4_plan.md:313` ("These
  types cannot be coordinate variables") and `:422` (refs);
  `docs/roadmap_v3.md:545,592` (Sprint 9) and `:603` (Sprint 10, refs);
  `docs/roadmap.md:977,1023` (same Sprint 9 text) and `:1034` (refs);
  `docs/NEXTCDF4_float16.md:25` ("No coordinate variables" rule);
  `docs/float16.md:27`; `docs/nextcdf4.md:242` (refs);
  `docs/refs.md:25` (refs); `docs/nextcdf4_status_v4_3_0.md:163`
  (refs non-goal). The status doc's gap 8 (line 123) already records
  #380 as resolved.
- `test/nextcdf4/tst_nextcdf4_var.c` has `test_coordinate` for
  `NC_FLOAT` (line 240); `test/nextcdf4/tst_nextcdf4_rename.c` has

## Work items

### 1. Fix in-session rename consistency in `src/nextcdf4/nxt4meta.c`

NEXTCDF-4's documented semantics (roadmap v3 Sprint 8, "Renaming a
coordinate variable also renames the underlying dimension" and vice
versa) keep the var/dim names in sync. Make in-session inquiry match:

- In `NEXTCDF4_rename_var` (~line 2277): move `dim =
  coord_var_dim(var)` to **before** `free(var->hdr.name)` /
  `var->hdr.name = strdup(name)` (before line 2350). The existing
  `if (dim)` block then executes as intended: it resyncs
  `dinfo->hdf_dataset` when the two handles differ (they always do —
  the coord var's scale is held open separately in `dinfo` and
  `vinfo`), calls `H5DSset_scale(dinfo->hdf_dataset, name)` to refresh
  the scale `NAME` attribute, updates `dim->hdr.name`, and rebuilds
  `grp->dim`'s index.
- In `NEXTCDF4_rename_dim` (~line 2210): replace the comment block at
  lines 2260–2263 with the symmetric sync — use `find_coord_var(grp,
  dim)` (line 2173) to find the coordinate variable, and when found
  update its `hdr.name` to `name` and `ncindexrebuild(grp->vars)`. No
  HDF5 link work is needed (the scale dataset link already moved; the
  var and dim share it). Correct the comment, which wrongly claimed
  upstream netcdf-c keeps the variable name unchanged — upstream
  instead *breaks* the coordinate relationship, which is not
  NEXTCDF-4's documented behavior.
- Tricky case: in `NEXTCDF4_rename_var`, `nc4_check_dup_name`
  (line 2309) must still run before any mutation, and the
  `!strcmp(var->hdr.name, name)` early return stays first. Renaming a
  coord var to a name matching a *different* dimension remains a plain
  rename (the dim sync only fires on the old pairing).

### 2. Extend `test/nextcdf4/tst_nextcdf4_var.c`

Add three test functions, wired into `main()` beside
`test_coordinate`, matching the file's existing `/** @return ... */`
per-test comment style and `unlink`/`nc_create(NC_NEXTCDF4|NC_CLOBBER)`
pattern. File name `tst_nextcdf4_var.h5` as today.

- `test_coord_bfloat16`: dim `"bx"` length 4; coord var `"bx"` of
  `NC_BFLOAT16`; dependent `NC_INT` var `"data"` on the same dim.
  Write four raw `uint16_t` bfloat16 patterns via `nc_put_var`; read
  back bit-exact via `nc_get_var`; read via `nc_get_var_float` and
  check the converted values; check `nc_inq_vardimid` on `data`.
  Close, reopen read-only, verify `nc_inq_vartype == NC_BFLOAT16`,
  `nc_inq_dimlen == 4`, and bit-exact values.
- `test_coord_float16_unlim`: `NC_UNLIMITED` dim `"t"`, coord var
  `"t"` of `NC_FLOAT16`. `nc_put_vara` two raw `uint16_t` values;
  `nc_inq_dimlen` reports 2. Close, reopen with `NC_WRITE`, verify
  len/type, `nc_put_vara` one more value at index 2, len becomes 3,
  values bit-exact.
- `test_coord_smallfloat_modes`: `NC_NEXTCDF4|NC_CLASSIC_MODEL` and
  `NC_NEXTCDF4|NC_NETCDF4_MODEL` creates each reject
  `nc_def_var("x", NC_BFLOAT16, 1, &dimid, ...)` with `NC_ENOTNC4`.
