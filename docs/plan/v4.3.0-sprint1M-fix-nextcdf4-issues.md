# v4.3.0 Sprint 1M: Issues

Source: docs/roadmap.md, "V4.3.0 / Sprint 1M".

## Goal

Close the four open NEXTCDF-4 defect issues: the installed
`nextcdf4dispatch.h` compiles outside the build tree (#378), def-var
setters stop destroying data (dataset recreation is deferred to a
single `_enddef` rebuild and post-commit setters return `NC_ELATEDEF`,
#382), `NC_BFLOAT16` fill values survive close/reopen (#377), and the
four `DISABLED` reopen tests run again under netcdf-c builds that lack
the upstream `USEFILEINFO` abort (#379).

## Decisions

| Topic | Decision |
|-------|----------|
| #382 rebuild timing | Defer setter-triggered dataset rebuilds to `_enddef` (Ed, 1a): setters mutate `NC_VAR_INFO_T`/`NEXTCDF4_VAR_INFO_T` state and set a dirty flag; `_enddef` rebuilds each dirty variable once. Closest to upstream's enddef-commit model; ≤1 recreation per variable ever. |
| #382 setter semantics | Upstream parity (Ed, 2a): `var->created` is set at `_enddef`; every DCPL setter (chunking, deflate, szip, fletcher32, filter, fill, endian) plus quantize then returns `NC_ELATEDEF`. `nc_put_att` `_FillValue` keeps its `var->written_to` → `NC_ELATEFILL` guard. |
| #377 `_FillValue` | Loads as a normal, user-visible attribute on datasets (Ed, 3a) — upstream parity (`nc_inq_att`/`nc_inq_attname` see it after reopen). `var->fill_value` on open comes from the `_FillValue` attribute when present, else the DCPL fill message. `nc_del_att`/`nc_rename_att` on `_FillValue` stay reserved-name rejections. |
| #379 / netcdf-c floor | Require the 64-slot UDF netcdf-c outright for NEXTCDF-4 (Ed, revised): `NEP_ENABLE_NEXTCDF4` fails configure with `FATAL_ERROR` unless the headers expose `NC_UDF` and `NC_MAX_UDF_FORMATS >= 64` (netcdf-c ≥4.10.2 / `main`); 10-slot builds are never supported. The four tests are re-enabled unconditionally — no gating. The project-wide `netcdf>=4.10.1` pkg floor stays for non-NEXTCDF-4 builds and bumps to 4.10.2 at release. |
| Freespace | No persistent free-space manager (Ed, 5a): deferred rebuilds bound orphaned object headers to ≤1 (~200–400 B) per variable; no on-disk format delta. |
| #378 header shape | Per the issue's proposed fix: installed header keeps only `NC_FORMATX_NEXTCDF4`, `NC_NEXTCDF4_initialize`, `NC_NEXTCDF4_finalize`; includes `<netcdf.h>`, `<netcdf_dispatch.h>`, `nep.h`. Dispatch-entry prototypes and `NEXTCDF4_dispatch_table` move to `src/nextcdf4/nxt4internal.h`. |

## Current state (2026-11-22)

All four defects were root-caused against the existing `build/`
(Debug, `NEP_ENABLE_NEXTCDF4=ON`, HDF5 2.1.1, `/usr/local/netcdf-c`
4.10.2-development — the 64-slot UDF build):

- **#378** — `include/nextcdf4dispatch.h` includes `config.h` (not
  installed) and `ncdispatch.h` (netcdf-c internal). It declares
  `NC_NEXTCDF4_initialize`/`finalize`, `NC_FORMATX_NEXTCDF4`,
  `NEXTCDF4_dispatch_table`, and seven dispatch-entry prototypes
  (`NEXTCDF4_create`/`open`/`abort`/`close`/`sync`/`inq_format`/
  `inq_format_extended`). All other dispatch entries are already
  declared in `src/nextcdf4/nxt4internal.h:160-290`, which is included
  by every backend `.c` file (`nxt4dispatch.c` includes both headers).
  `nep.h` is standalone (`<stdio.h>`, `<stdint.h>`, `<netcdf.h>`,
  `<netcdf_filter.h>`); `<netcdf_dispatch.h>` is installed by
  netcdf-c. Six other *installed* dispatch headers share the same
  `config.h`/`ncdispatch.h` defect (`grib2dispatch.h`,
  `fitsdispatch.h`, `pds4dispatch.h`, `dicomdispatch.h`,
  `pdbdispatch.h`, `mmcifdispatch.h`) — filed as #389, not this sprint.
- **#382** — every def-var setter calls `nx4_create_var_dataset()`
  (`nxt4meta.c:1443`, called from `nxt4meta.c:1696,1740,1772,2169` and
  `nxt4filter.c:120,178,218`), which `H5Dclose`/`H5Ldelete`s the
  dataset and recreates it. Verified damage beyond the issue text:
  - User attributes are destroyed by recreation (the dataset and its
    attributes are deleted; only the two hidden id attributes are
    rewritten). Probe: `nc_put_att` then `nc_def_var_fill` → reopen
    shows `natts=0`.
  - `var->created` is set only in `load_one_var`
    (`nxt4meta.c:3576`), never in-session — so the existing
    `NC_ELATEDEF` guards in `nxt4filter.c:64,158,209` never fire, and
    write → redef → setter silently deletes written data.
  - `def_var_chunking`/`def_var_fill`/`def_var_endian`/
    `def_var_quantize` have no `created`/`written_to` guards at all.
  - `H5DSdetach_scale` is never called on the recreation path — the
    dimension scales' `REFERENCE_LIST` attributes accumulate dead
    references (the issue's "4 entries instead of 3"), and a
    coordinate variable's *dependents* keep `DIMENSION_LIST` entries
    pointing at the orphaned object.
  - `nx4_rewrite_atts` (`nxt4meta.c:2037`) and `nx4_reattach_dim`
    (`nxt4meta.c:2493`, used by the Sprint 1L2 rename path) already
    implement the att-rewrite and detach/reattach machinery a rebuild
    needs. `NEXTCDF4__enddef` (`nxt4file.c:502`) currently only calls
    `NEXTCDF4_write_types` + `H5Fflush`. `var->written_to` is set at
    `nxt4io.c:353`.
- **#377** — verified with probes: the `_FillValue` *attribute* is
  written correctly (0x7f00 on disk), and `nc_put_att(..., NC_BFLOAT16,
  "_FillValue", ...)` now succeeds (Sprint 1L2 fixed the `NC_EBADNAME`
  part). The bug is `H5Tget_native_type()` on NEP-only types:
  `H5Tget_native_type(H5T_FLOAT_BFLOAT16LE)` returns a 4-byte native
  float (nearest convertible type), so `nx4_dcpl_fill`
  (`nxt4meta.c:1411`) passes a 2-byte buffer where HDF5 reads 4 bytes
  (heap over-read → stores 0), and `load_one_var`
  (`nxt4meta.c:3611`) `H5Pget_fill_value`s into a 2-byte buffer with a
  4-byte mem type (heap overflow → `var->fill_value` garbage/0). Same
  hazard for FP8/FP6/FP4 fills. On reopen `_FillValue` is filtered as
  reserved so `nc_inq_att` returns `NC_ENOTATT` — upstream exposes it
  as a normal attribute.
- **#379** — root cause found in upstream history: before
  `netcdf-c@5a81fb791` (the 64-slot UDF rework), `FILEINFOFLAGS`
  covered only `NC_FORMATX_UDF0`/`UDF1`; `assert(USEFILEINFO(nc))` in
  `NC_reclaim_data` (`libdispatch/dinstance_intern.c:97`) therefore
  aborts for *any* UDF slot ≥2 on reclaim paths. The range-based
  `UDFMODEL` in that commit covers all slots. Verified: all four
  disabled tests (`tst_nextcdf4_float16`, `tst_nextcdf4_complex`,
  `tst_nextcdf4_bitfield`, `tst_explore` — `tst_nextcdf4_ref`,
  `tst_nextcdf4_rename`, `tst_rename` were re-enabled in 1L2) pass
  under the installed 64-slot 4.10.2-dev. Under
  `/usr/local/netcdf-c-4.10.1` they cannot even register: `NC_UDF9`
  is `0x2000000` in the 10-slot scheme vs `0x480040` in the 64-slot
  scheme — a build is bound to one scheme at compile time.
- `test/nextcdf4/CMakeLists.txt` disables exactly four tests with
  `DISABLED TRUE` (float16, complex, bitfield, `tst_explore`).
- The subgroup name-collision edge flagged for 1M by Sprint 1L1 is
  already fixed — `var->dim[0]->container == grp` (`nxt4meta.c:1246`,
  added in 1L2) verified by probe: a subgroup var named like an
  ancestor group's dimension defines cleanly. Only the stale status-doc
  line remains.
- `NEXTCDF4_write_attributes` is declared in `nxt4internal.h:291` but
  never defined — dead declaration.
- CI: `nextcdf4.yml` pins netcdf-c `5baa62e6` (64-slot) and runs the
  full `ctest`; `spack.yml` builds `^netcdf-c@main` with
  `install --test=root`. Enabled tests run in both automatically.
- NEP occupies all ten UDF slots (`nep.h` slot table: UDF0–UDF9), so
  every backend ≥slot 2 carries the same latent `USEFILEINFO` abort on
  10-slot netcdf-c — but only NEXTCDF-4's tests actually hit
  `NC_reclaim_data` today, so the hard requirement is scoped to
  `NEP_ENABLE_NEXTCDF4`; the project-wide floor bumps at the 4.10.2
  release.
- Spack impact: the overlay recipe's netcdf-c minimum must follow —
  `depends_on("netcdf-c@4.10.2:", when="+nextcdf4 @4.3.0:")` (work item
  7). Conda is unaffected: `conda/recipe/recipe.yaml` does not enable
  NEXTCDF-4 (its test asserts `libncnextcdf4` is absent) and keeps the
  `libnetcdf >=4.10.1` floor until the project-wide bump.

### 1. Make `include/nextcdf4dispatch.h` self-contained (#378)

- Remove `#include "config.h"` and `#include "ncdispatch.h"`; add
  `#include <netcdf.h>` then `#include <netcdf_dispatch.h>` before the
  existing `#include "nep.h"` (order matters — `netcdf_dispatch.h`
  needs `netcdf.h` types).
- Keep in the installed header: the `NC_FORMATX_NEXTCDF4` define,
  `NC_NEXTCDF4_initialize()` (returns `NC_Dispatch *` — hence
  `netcdf_dispatch.h`), `NC_NEXTCDF4_finalize()`. Reword the `/** @file`
  block: it no longer declares dispatch-table entries.
- Move to `nxt4internal.h`: `NEXTCDF4_create`, `NEXTCDF4_open`,
  `NEXTCDF4_abort`, `NEXTCDF4_close`, `NEXTCDF4_sync`,
  `NEXTCDF4_inq_format`, `NEXTCDF4_inq_format_extended`, and
  `extern const NC_Dispatch *NEXTCDF4_dispatch_table`. All consumers
  (`nxt4dispatch.c`, `nxt4ref.c` via `nxt4internal.h`, tests using only
  `NC_NEXTCDF4_initialize`) are unaffected.
- `docs/nextcdf4.md`: note that applications may now include the
  installed header to call `NC_NEXTCDF4_initialize()` explicitly
  (alternative to `.ncrc` autoload). `docs/nextcdf4_architecture.md`
  mentions the header — keep text accurate after the split.
- Remove the dead `NEXTCDF4_write_attributes` declaration in
  `nxt4internal.h` while editing it (no definition exists).

### 2. Defer setter-triggered dataset rebuilds to `_enddef` (#382)

- `nxt4internal.h`: add `int dcpl_dirty;` to `NEXTCDF4_VAR_INFO_T`.
- `nx4_find_var_for_write()` (`nxt4meta.c:1625`): after the
  define-mode checks add `if ((*var)->created) return NC_ELATEDEF;` —
  one guard covering chunking, fill, endian, all filter setters, and
  quantize (upstream `nc_def_var_extra` guards them all). Delete the
  now-redundant `var->created` checks in `nxt4filter.c:64,158,209`.
- Replace each setter's `nx4_create_var_dataset()` call with
  `vinfo->dcpl_dirty = 1; return NC_NOERR;`:
  `NEXTCDF4_def_var_chunking` (`nxt4meta.c:1696`),
  `NEXTCDF4_def_var_fill` (`1740`), `NEXTCDF4_def_var_endian` (`1772`),
  and `nxt4filter.c:120,178,218`. Setters still record their settings
  on `var`/`var->filters` immediately so in-session inquiries are
  unchanged.
- `put_att` `_FillValue` path (`nxt4meta.c:2155-2173`): stop calling
  `nx4_create_var_dataset`. Mirror the value into `var->fill_value`
  (as now), set `vinfo->dcpl_dirty = 1` **only when `!var->created`**
  (pre-commit the DCPL rebuild picks it up; post-commit the DCPL is
  immutable anyway — the attribute + `var->fill_value` carry it, the
  upstream quirk), then write the attribute on the existing dataset.
  Keep the `written_to` → `NC_ELATEFILL` guard.
- `nx4_create_var_dataset()` (`nxt4meta.c:1443`) gains rebuild hygiene
  when `vinfo->hdf_dataset >= 0` (recreation only):
  - Non-coordinate var: `H5DSdetach_scale(vinfo->hdf_dataset,
    dinfo->hdf_dataset, i)` for each dim before `H5Dclose`/`H5Ldelete`
    — removes the var's `DIMENSION_LIST` entry and the scale's
    `REFERENCE_LIST` entry.
  - Coordinate var (its dataset *is* the scale): call
    `nx4_reattach_dim(grp, dim, old_dset, -1, var)` before delete to
    detach dependents from the doomed object; after recreation +
    `H5DSset_scale`, call `nx4_reattach_dim(grp, dim, -1, new_dset,
    var)` to re-attach them. Reuse `nx4_reattach_dim`
    (`nxt4meta.c:2493`) — it tolerates a `-1` side already.
  - After recreation: `nx4_rewrite_atts(vinfo->hdf_dataset,
    var->att)` — restores user attributes (including `_FillValue`) in
    index order after the hidden id attributes are rewritten.
  - Apply the same `nx4_reattach_dim` fix to the *first*-creation
    coordinate-var path in `NEXTCDF4_def_var` (`nxt4meta.c:1280-1294`):
    dependents defined before the coord var currently keep
    `DIMENSION_LIST` entries pointing at the deleted placeholder
    scale.
- `NEXTCDF4__enddef` (`nxt4file.c:502`): after
  `NEXTCDF4_write_types`, walk all groups recursively; for each var
  with `vinfo->dcpl_dirty` call `nx4_create_var_dataset` and clear the
  flag; then set `var->created = 1` on every var with a live dataset.
  This also runs inside `NEXTCDF4_close`'s implicit `_enddef` — same
  semantics as today.
- Update the doc blocks that describe recreation
  (`nx4_create_var_dataset`, the setters, `NEXTCDF4_VAR_INFO_T`) and
  delete the stale "(Known defect #377…)" comment at
  `nxt4meta.c:1704`.

### 3. Fix fill value for NEP-only types and load `_FillValue` as a normal attribute (#377)

- `nx4_dcpl_fill` (`nxt4meta.c:1410`): when
  `var->type_info->hdr.id > NC_STRING`, pass `hdf_type` itself to
  `H5Pset_fill_value` — `fillp` holds raw file-format bits, and
  `H5Tget_native_type` widens NEP types (bf16→native f32 → over-read).
  Keep `H5Tget_native_type` for ids ≤ `NC_STRING` (upstream parity).
- `load_one_var` (`nxt4meta.c:3611`): for `id > NC_STRING` pass
  `ftype` (the dataset's own datatype) to `H5Pget_fill_value` —
  writes `fsize` bytes into the `fsize`-byte `var->fill_value`. Keep
  the native-type mem type for standard types.
- `_FillValue` visibility: in the attribute-load callback
  (`nxt4meta.c` `load_att_cb`/`read_hdf5_att` area ~3700), skip
  reserved attributes exactly as now **except** `_FillValue` on a
  dataset — load it via `read_hdf5_att` so it appears in `var->att`.
  Group-level `_FillValue` stays filtered (upstream ignores a global
  `_FillValue`).
- After attribute load for a var, if a `_FillValue` att exists copy
  its value into `var->fill_value` (attribute is authoritative; DCPL
  recovery fills the `NULL` case) — `nc_inq_var_fill` then reports the
  user's value and unwritten elements read back the DCPL fill.
- `is_reserved_att` still lists `_FillValue` for `put_att`
  interception and `del_att`/`rename_att` rejection — only the *load*
  filter exempts it on datasets.
- Behavior to verify per the issue: `nc_def_var_fill` round-trip on
  `NC_BFLOAT16` (0x7f00 survives close/reopen), `_FillValue` via
  `nc_put_att` visible after reopen, `NC_FLOAT16` and the 8-bit types
  (FP8/FP6/FP4 now store user fill bits correctly through the same
  path), `NC_STD_REF` still skips fill.
