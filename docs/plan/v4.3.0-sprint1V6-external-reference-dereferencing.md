# V4.3.0 Sprint 1V6: External Reference Dereferencing

Source: docs/roadmap.md, "V4.3.0 - NEXTCDF4 Development / Sprint 1V6".

## Goal

A NEP application can store an `NC_STD_REF` token that points into a
different file and later follow it entirely through the NetCDF API:
a new `nc_ref_open_target` opens the external target file as a
caller-owned NEXTCDF-4 session, and the existing `nc_deref_object`,
`nc_deref_region` and `nc_deref_attr` calls resolve variables, groups,
committed datatypes and attributes on that target session instead of
returning `NC_ENOTNC4`. External filenames must be absolute and target
files must be writable by the application; the on-disk
`H5T_STD_REF`/`nc_std_ref_t` format is unchanged.

## Decisions

| Topic | Decision |
|---|---|
| Ed's answers | `1a 2a 3a 4a` (accept all recommendations). |
| API shape (1a) | New `nc_ref_open_target(int ncid, const nc_std_ref_t *ref, int *target_ncidp)` in `include/nep.h`. It opens the external file and returns a NetCDF file ID; the caller then calls the existing `nc_deref_*` functions with that `target_ncid`. No combined open+dereference functions, no caller-supplied sessions required. |
| Ownership/lifetime (2a) | Each successful `nc_ref_open_target` returns an independent session the caller owns and must close with `nc_close`. No caching, no shared handles, no borrowing of caller sessions. IDs returned by `nc_deref_*` are valid until `target_ncid` is closed; token lifetime (`nc_ref_free`) is independent of target-handle lifetime. |
| Writable targets | External targets must be openable read-write. HDF5 2.1.1's internal reopen of persisted external references may request `H5F_ACC_RDWR`; we do not promise a read-only open. Dereferencing must not intentionally modify target contents. Read-only targets are out of scope. |
| Absolute filenames | `nc_ref_object_ext`, `nc_ref_region_ext` and `nc_ref_attr_ext` require an absolute filesystem filename (`filename[0] == '/'`); relative names return `NC_EINVAL`. `nc_ref_open_target` also rejects tokens whose stored filename is relative with `NC_EINVAL`. No process working-directory dependence; the containing file's directory is never consulted. |
| Target file kind | The target must be openable by NEXTCDF-4 (`nc_open` with `NC_NEXTCDF4|NC_WRITE`). Native and `NC_NETCDF4_MODEL` compatible NetCDF-4 files are supported; arbitrary non-NetCDF HDF5 files are out of scope. |
| Datatype attributes (3a) | For attribute references whose owner is a committed datatype, `nc_deref_attr` resolves the owner's `NC_REF_OBJ_NCTYPE`/`typeid` and returns the attribute name via the existing signature; reading the value is done by the application through raw HDF5 (`H5Aopen`/`H5Aread`). No new attribute-read API this sprint. |
| Tests (4a) | New executable `test/nextcdf4/tst_nextcdf4_ref_external.c` under a new `nextcdf4_ref` label, separate from `tst_nextcdf4_ref`. |
| Unreleased API | No compatibility obligation: existing external-reference behavior (the `NC_ENOTNC4` rejection and relative-name handling) may be replaced. |
| Packaging | No new CMake option, dependency floor, installed file, plugin path or variant: one function joins `nep.h`/`libncnextcdf4`. No Spack/conda change. |
| Release | Sprint 2 owns release notes, tag and packaging publication. No implementation, commit or push during refinement. |

## Current state (2026-11-27)

- Sprint 1L unified reference types are implemented:
  `docs/plan/v4.3.0-sprint1L-reference-types.md`. `NC_STD_REF = 30`,
  `NC_STD_REF_SIZE = 64`, and `nc_std_ref_t` is layout-compatible with
  HDF5 2.1.1's `H5R_ref_t`. Kinds: `NC_REF_OBJECT`, `NC_REF_REGION`,
  `NC_REF_ATTR`; owner kinds include `NC_REF_OBJ_VAR`, `NC_REF_OBJ_GRP`,
  `NC_REF_OBJ_NCTYPE`.
- `include/nep.h:418-655` declares the full reference API with Doxygen
  blocks: `nc_ref_object`/`nc_ref_region`/`nc_ref_attr` (in-file),
  `nc_ref_object_ext`/`nc_ref_region_ext`/`nc_ref_attr_ext`
  (cross-file creators), `nc_deref_object`/`nc_deref_region`/
  `nc_deref_attr`, and `nc_ref_get_type`/`nc_ref_get_file_name`/
  `nc_ref_get_obj_name`/`nc_ref_free`.
- `src/nextcdf4/nxt4ref.c` implements the API. `ref_file` (line 43)
  maps `ncid` to `NEXTCDF4_FILE_INFO_T` and rejects non-NEXTCDF-4 files;
  `ref_check_native` (line 73) rejects compatibility-mode files for
  reference creation and returns `NC_EPERM` during active SWMR.
  `ext_open` (line 768) currently calls
  `H5Fopen(filename, H5F_ACC_RDONLY, H5P_DEFAULT)` for external
  creators and does not check for absolute paths.
- `nc_deref_object` (line 434), `nc_deref_region` (line 560) and
  `nc_deref_attr` (line 699) call `H5Ropen_object`/`H5Ropen_region`/
  `H5Ropen_attr` and map results against the containing file's metadata.
  External references currently fail here: the opened HDF5 ID belongs to
  a different file and lookup against `file` metadata fails, surfacing
  as `NC_ENOTNC4`.
- Verified HDF5 2.1.1 behavior (local source
  `/home/ed/local/hdf5-2.1.1_mpi-src`): reopening a persisted external
  token internally uses `H5F_ACC_RDWR` and the stored filename verbatim;
  there is a `TODO` for search paths and no public API to bind a token
  to an already-open file. Hence the writable-target and
  absolute-filename requirements.
- `test/nextcdf4/tst_nextcdf4_ref.c` currently covers external creation,
  persisted external tokens, the `NC_ENOTNC4` deref rejection, raw HDF5
  external reopening and compatibility-mode rejection. Registered in
  `test/nextcdf4/CMakeLists.txt`.
- `docs/refs.md` documents external references as inspectable/raw-HDF5
  only and says `nc_deref_*` returns `NC_ENOTNC4` — this sprint replaces
  that contract. `docs/nextcdf4.md`, `docs/design.md`, `docs/prd.md`
  and `docs/prfaq.md` describe reference support.
- No Spack or conda contract changes: the sprint adds one public
  function and changes behavior only, so
  `spack/repos/spack_repo/nep/packages/nep/package.py` needs nothing.
- Tools verified locally: CMake 3.28.3, GCC 13.3.0, Doxygen 1.9.8,
  NetCDF-C 4.10.2-development, HDF5 2.1.1 (serial and MPI installs).

## Work items

### 1. Public API: `nc_ref_open_target`

- `include/nep.h`: declare
  `int nc_ref_open_target(int ncid, const nc_std_ref_t *ref, int *target_ncidp);`
  near the other reference functions (after the `nc_ref_*_ext` block).
  Full Doxygen block, `@author Edward Hartnett, Intelligent Data Design, Inc.`
- Contract in the Doxygen block and `docs/refs.md`:
  - `ncid` must be a NEXTCDF-4 file (validated via `ref_file`).
  - `ref` must be a valid external token (`H5Rget_type` returns an
    object/region/attribute kind and `H5Rget_file_name` yields a
    filename); internal in-file tokens return `NC_EINVAL`.
  - The stored filename must be absolute; otherwise `NC_EINVAL`.
  - The target is opened with `nc_open(filename, NC_NEXTCDF4|NC_WRITE,
    &target_ncid)`. Non-NetCDF-4/unreadable targets propagate the
    `nc_open` error (`NC_ENOTNC4`/`NC_EPERM` as produced); the
    read-write requirement is documented.
  - On success the caller owns `*target_ncid` and must `nc_close` it.
    Repeated calls return independent sessions. On failure
    `*target_ncidp` is set to -1 and nothing is left open.
  - Token release stays with `nc_ref_free`; freeing the token does not
    close the target session and vice versa.

### 2. Absolute-filename enforcement in creators

- `src/nextcdf4/nxt4ref.c`, `ext_open` (line 768): reject
  `filename == NULL` or `filename[0] != '/'` with `NC_EINVAL` before
  `H5Fopen`. Switch the open flags to `H5F_ACC_RDWR` so creation fails
  early on targets that cannot satisfy the writable-target contract
  (the token would otherwise be undereferenceable later). Update the
  three `nc_ref_*_ext` Doxygen blocks to state the absolute-path and
  writable-target requirements.

### 3. External dereference resolution in `nxt4ref.c`

- `nc_deref_object`, `nc_deref_region`, `nc_deref_attr`: when the token
  is external (detect via `H5Rget_file_name` returning a non-empty
  name), the `ncid` argument is the target session returned by
  `nc_ref_open_target`. After `H5Ropen_*` succeeds, map the opened HDF5
  object/dataspace against that file's `NEXTCDF4_FILE_INFO_T` metadata
  (same lookup path used for in-file refs — compare opened HDF5 object
  identity, e.g. `H5Oget_info` token/`H5Requal`, not the stored object
  path, so renamed objects still resolve).
- Guard: if `ncid` is a NEXTCDF-4 file but the opened object does not
  belong to that file's HDF5 file (caller passed the containing file's
  ncid, or a different target), fail deterministically with
  `NC_EINVAL` rather than returning wrong IDs. Use `H5Rget_file_name`
  vs the session's recorded path, or verify the opened object's file
  (`H5Iget_file_id`) matches the session's HDF5 file handle.
- `nc_deref_region`: keep regular strided hyperslab semantics. Recover
  `start`/`count`/`stride` from the token's region selection
  (`H5Rget_region`/`H5Sget_regular_hyperslab`); irregular selections
  return `NC_EINVAL` (already out of scope for creation). The returned
  `varid`/`grpid` belong to `target_ncid` and die with it.
- `nc_deref_attr`: for a committed-datatype owner return
  `NC_REF_OBJ_NCTYPE` plus `typeid` and the attribute name only (decision
  3a); variable and group owners resolve fully as today.
- No recursive traversal of reference graphs.
- Error mapping (document in `docs/refs.md`): `NC_EINVAL` for relative
  stored filename, in-file token passed to `nc_ref_open_target`, wrong
  token kind, irregular region, wrong-target ncid; `NC_ENOTNC4` when
  the target is not a NEXTCDF-4-readable NetCDF-4 file; `NC_EPERM` for
  permission failures; other `nc_open`/`H5R*` failures propagate their
  existing codes. All failure paths release any opened HDF5 IDs via the
  existing `fail:`/`EBAIL` cleanup style.

### 4. Tests: `test/nextcdf4/tst_nextcdf4_ref_external.c`

New executable registered in `test/nextcdf4/CMakeLists.txt` with label
`nextcdf4_ref` (plain comments, `Author:` line, no Doxygen). Fixtures:
a containing file and a target file created in the test's working
directory, referenced by absolute path (build via `getcwd` + name, or
`realpath`). Cases:

- `nc_ref_object_ext` to a variable in a nested group, persist token,
  close both files, reopen containing file, `nc_ref_open_target`,
  `nc_deref_object`, `nc_get_var` through the returned IDs, `nc_close`
  target, `nc_ref_free`.
- `nc_ref_region_ext` with strided hyperslab; `nc_deref_region` recovers
  `start`/`count`/`stride` and data reads match the original selection.
- `nc_ref_attr_ext` on a variable and on a group; `nc_deref_attr`
  returns owner kind + `att_name`, value read via `nc_get_att*` on the
  target session. Committed-datatype owner: `NC_REF_OBJ_NCTYPE`/`typeid`
  + name returned; value verified via raw HDF5 (`H5Aopen`/`H5Aread`).
- Group object and committed-datatype object references.
- Rename/object-identity: `nc_rename_var` in the target between
  creation and dereference still resolves.
- Repeated dereferences: two `nc_ref_open_target` calls yield two
  independent sessions; each usable and each closeable.
- Close ordering: dereferenced IDs invalid after target `nc_close`
  (test only that no crash occurs on close; document the lifetime rule).
- Negative cases: relative filename to `nc_ref_*_ext` → `NC_EINVAL`;
  token with relative stored filename → `NC_EINVAL` from
  `nc_ref_open_target`; in-file token → `NC_EINVAL`; missing target
  file → `nc_open` error; read-only target file (chmod 0444) →
  documented failure (`NC_EPERM`-family); `nc_deref_*` called with the
  containing file's ncid on an external token → `NC_EINVAL`; wrong
  token kinds. Each negative path leaves no leaked HDF5 IDs
  (verifiable by subsequent clean `nc_close`).
- Working-directory independence: after creating files, `chdir` to a
  scratch directory before deref; absolute paths still resolve.
- Keep `tst_nextcdf4_ref` covering in-file behavior; remove/adjust its
  external-deref `NC_ENOTNC4` expectation to the new contract
  (external token + containing ncid → `NC_EINVAL`).

## Out of scope

- Read-only external targets (needs an HDF5 mechanism that does not
  reopen RDWR; revisit when HDF5 provides one — future work beyond
  v4.3.0).
- Relative target filenames, containing-file-relative resolution and
  automatic relocation of moved targets (same future work).
- Legacy HDF5 reference datatypes (`H5T_STD_REF_OBJ`,
  `H5T_STD_REF_DSETREG`, `hobj_ref_t`, `hdset_reg_reg_t`) — permanently.
- References nested in compounds/vlens; irregular region selections —
  existing Sprint 1L limitations, unchanged.
- Reading committed-datatype attribute values through NetCDF (raw HDF5
  only this sprint).
- Parallel reference I/O, reference data under SWMR, Fortran wrappers —
  unchanged prior deferrals.
- Arbitrary non-NetCDF HDF5 target mapping.
