# NEP v4.1.0 - NEXTCDF4 Tools and Examples

> Continues the NEXTCDF-4 work from v4.0.0 by adding user-facing tooling, language bindings, and the documentation and logging infrastructure needed to support them.

This release focuses on making the NEXTCDF-4 backend accessible to users and downstream developers through documentation, logging, tools (`nextcopy` / `nextdump`), and language bindings. The full NEXTCDF-4 backend implementation was completed in v4.0.0.

---

## Highlights

- **Complete NEXTCDF-4 user and developer documentation**: dedicated reference page, Doxygen integration, and updates to design, PRD, FAQ, and release notes.
- **NEP logging framework**: unified `LOG(())` macro for the NEXTCDF-4 backend and NEP handlers, activated when netcdf-c logging is enabled.
- **`nextcopy` and `nextdump` tools**: copy and inspect NEXTCDF-4 files with support for all NEXTCDF-4 types and compatibility modes.
- **Fortran and language bindings**: expose new C APIs and datatypes through maintained language bindings.
- **Compatibility and release validation**: broad NetCDF-C compatibility testing, interoperability checks, regression tests, and performance/resource-leak validation across supported HDF5 versions.

## Sprint 2: Logging in NEP

### Implementation

- CMake now probes the installed NetCDF-C for `NC_HAS_LOGGING` and defines the build-time `LOGGING` macro only when NetCDF-C was built with logging support. The feature is exported through `nep_meta.h` as `NEP_HAS_LOGGING`.
- Added `include/nc_logging.h`, a NEP copy of the NetCDF-C logging header, providing:
  - `LOG((severity, fmt, ...))` → `nc_log(...)` when logging is enabled.
  - No-op `LOG(...)` expansion when logging is disabled, so release builds have zero runtime overhead.
  - `BAIL`, `BAILLOG`, and `BAIL_QUIET` macros matching the netcdf-c convention.
- Added `src/nextcdf4/nxt4err.h` with NEXTCDF-4-specific `BAIL` and HDF5-aware `BAIL2` macros that set `ret`, log the error, optionally dump the HDF5 error stack via `nc_log_hdf5()`, and jump to the existing `fail:` cleanup labels.
- Wired logging into the NEXTCDF-4 backend:
  - `NC_NEXTCDF4_initialize()` reads `NETCDF_LOG_LEVEL` and calls `nc_set_log_level()`.
  - Lifecycle functions (`create`, `open`, `close`, `abort`, `sync`, `enddef`, `redef`, `inq_format*`) emit entry/exit diagnostics.
  - Metadata functions (`def_dim`, `def_var`, `load_metadata`) log their calls and key parameters.
  - Replaced temporary `fprintf(stderr, ...)` debug statements in `nxt4create.c`, `nxt4open.c`, and `nxt4file.c`.
- Added `test/nextcdf4/tst_nextcdf4_logging.c` which verifies:
  - Log output appears at level 3 and contains expected lifecycle messages.
  - Output disappears after `nc_set_log_level(-1)`.
  - An HDF5 open failure emits a severity-0 error line.
  - The test skips cleanly when `LOGGING` is not defined.

### Documentation

- Added a "Diagnostics and Logging" section to `docs/nextcdf4.md` explaining how to enable logging, severity levels, and which operations are instrumented.

## Dependencies

- netcdf-c built with UDF plugin and `NC_Dispatch` support.
- HDF5 1.14.0 or newer (required for NEXTCDF-4).
- HDF5 2.1.1 or newer (recommended for small floating-point and complex types).
