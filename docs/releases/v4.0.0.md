# NEP v4.0.0 - NEXTCDF4

> Introduces NEXTCDF-4, a clean-room rewrite of the NetCDF-4/HDF5 backend delivered as an opt-in NEP UDF expansion pack. NEXTCDF-4 supports the full enhanced NetCDF-4 data model, variable I/O, storage features, and new atomic types.

This release adds a new UDF backend that coexists with netcdf-c's built-in HDF5 backend. Files are selected explicitly with `NC_NEXTCDF4`; the backend is also discoverable through the UDF9 autoload path. The complete architecture, compatibility contract, and type roadmap are defined in `docs/plan/NEXTCDF4_plan.md`.

---

## Highlights

- **NEXTCDF-4 UDF backend** registered on UDF9 with autoload support.
- **Full NetCDF-4 file lifecycle**: `nc_create`, `nc_open`, `nc_close`, and `nc_abort` for native, classic-model, and `NC_NETCDF4_MODEL` files.
- **Core metadata model**: dimensions, variables, global/variable attributes, groups, and user-defined types.
- **Variable I/O and dimension scales**: `nc_put_vara`/`nc_get_vara`, `nc_put_var`/`nc_get_var`, `nc_put_var1`/`nc_get_var1`, and `nc_put_vars`/`nc_get_vars` (mapped I/O is intentionally deprecated).
- **Variable storage features**: chunking, fill values, deflate+shuffle, Fletcher32, endianness, and quantization.
- **Interoperability**: open files written by NEXTCDF-4 and by upstream `NC_NETCDF4` with dimension-scale fallback discovery.
- **New atomic types**: small floating-point (`NC_FLOAT16`, `NC_BFLOAT16`, `NC_FLOAT8_*`, `NC_FLOAT6_*`, `NC_FLOAT4_*`), complex (`NC_COMPLEX`, `NC_DOUBLECOMPLEX`), bitfields (`NC_BITFIELD8/16/32/64`), and reference (`NC_REF_OBJECT`, `NC_REF_REGION`) types.

## Features

### NEXTCDF-4 Foundation (Sprint 1)

- Reserves UDF9 as `NEP_UDF_NEXTCDF4` with the public alias `NC_NEXTCDF4`.
- Adds the `NEP_ENABLE_NEXTCDF4` CMake option, disabled by default, gated on a netcdf-c build that supports UDF plugins and `NC_Dispatch`, plus HDF5 1.14.0 or newer.
- Exposes `NEP_HAS_NEXTCDF4` through `nep_meta.h`.
- Adds `.ncrc`/autoload metadata for `NETCDF.UDF9.LIBRARY` and `NETCDF.UDF9.INIT`.

### File Lifecycle (Sprint 2)

- `nc_create(..., NC_NEXTCDF4 | NC_CLOBBER, ...)` and `nc_open(..., NC_NEXTCDF4 | NC_NOWRITE/NC_WRITE, ...)` for empty NEXTCDF-4 files.
- Writes `_Nextcdf4Backend` and, in `NC_NETCDF4_MODEL` mode, `_Nextcdf4Model` markers.
- `NC_NETCDF4_MODEL` uses HDF5 1.10 library-version bounds for compatibility with upstream netcdf-c.
- Native and `NC_CLASSIC_MODEL` files use the latest HDF5 format bounds (Superblock v3).

### Core Metadata Model (Sprint 3)

- Dimensions, fixed-size atomic variables, global and variable attributes.
- `nc_redef`/`nc_enddef` transitions and define-mode enforcement.
- Stable dimension and variable IDs across create/close/reopen.
- Hidden attribute filtering so backend markers never appear as user attributes.

### Variable I/O and Dimension Scales (Sprint 4)

- Full atomic variable `put`/`get` surface except `nc_put_varm`/`nc_get_varm` (deprecated and unimplemented).
- HDF5 dimension-scale attachment, `DIMENSION_LIST`/`REFERENCE_LIST`, and `_Netcdf4Coordinates`.
- Unlimited-dimension extension and coordinate-variable support.

### Groups and User-Defined Types (Sprint 5)

- Arbitrarily nested groups with parent/child inquiry and full-name lookup.
- Compound, enum, opaque, vlen, and `NC_STRING` user-defined types.
- Attribute and variable I/O for all new types.

### Variable Storage Features (Sprint 6)

- `nc_def_var_chunking`, `nc_def_var_deflate`, `nc_def_var_fletcher32`.
- `nc_def_var_fill`, `nc_inq_var_fill`, `NC_NOFILL`.
- `nc_def_var_endian` (little, big, native).
- `nc_def_var_quantize` with `NC_QUANTIZE_BITGROOM`, `NC_QUANTIZE_GRANULARBR`, and `NC_QUANTIZE_BITROUND`.
- DCPL properties are recovered when an existing file is reopened.

### Open Existing and Populated Files (Sprint 7)

- `nc_open` for files previously written by `NC_NEXTCDF4` and for upstream `NC_NETCDF4` files.
- Dimension mapping prefers `_Netcdf4Coordinates`, falls back to `DIMENSION_LIST`/`REFERENCE_LIST`, and finally to `NAME`/`CLASS` dimension-scale matching.
- Recursive group, variable, attribute, and type loading.

### Correct Dimension and Variable Renaming (Sprint 8)

- `nc_rename_dim` and `nc_rename_var` in define mode.
- Coordinate-variable rename keeps the shared dimension-scale dataset and link name in sync.
- Shared dimensions rename without breaking dependent variables.

### Small Floating-Point Types (Sprint 9)

- `NC_FLOAT16` (IEEE 754 binary16).
- `NC_BFLOAT16`, `NC_FLOAT8_E4M3`, `NC_FLOAT8_E5M2`, `NC_FLOAT6_E2M3`, `NC_FLOAT6_E3M2`, `NC_FLOAT4_E2M1` (when linked against HDF5 2.1.1 or later).
- Raw bit-pattern round-trip using `nc_put_vara`/`nc_get_vara`.

### Complex, Bitfield, and Reference Types (Sprint 10)

- `NC_COMPLEX` and `NC_DOUBLECOMPLEX` stored as HDF5 compound `r`/`i` pairs.
- `NC_BITFIELD8/16/32/64` as fixed-width unsigned bitfields.
- `NC_REF_OBJECT` and `NC_REF_REGION` stored as opaque HDF5 object/region reference tokens.

## API Changes

- New format-selection flag: `NC_NEXTCDF4`.
- New model flag: `NC_NETCDF4_MODEL`.
- New atomic `nc_type` constants: `NC_FLOAT16`, `NC_BFLOAT16`, `NC_FLOAT8_E4M3`, `NC_FLOAT8_E5M2`, `NC_FLOAT6_E2M3`, `NC_FLOAT6_E3M2`, `NC_FLOAT4_E2M1`, `NC_COMPLEX`, `NC_DOUBLECOMPLEX`, `NC_BITFIELD8`, `NC_BITFIELD16`, `NC_BITFIELD32`, `NC_BITFIELD64`, `NC_REF_OBJECT`, and `NC_REF_REGION`.

---

## Build System

- `CMakeLists.txt` adds `NEP_ENABLE_NEXTCDF4`, disabled by default.
- HDF5 1.14.0 or newer is required to enable NEXTCDF-4.
- HDF5 2.1.1 or newer is recommended for the small floating-point types.
- `nep_meta.h` exposes `NEP_HAS_NEXTCDF4` when the backend is built.

---

## Known Limitations

- `NC_NEXTCDF4` remains an explicit selection; there is no magic-number dispatch for HDF5 files.
- `nc_put_varm`/`nc_get_varm` are not implemented (deprecated in NEXTCDF-4).
- Object and region reference types round-trip as opaque tokens; no NetCDF dereferencing API is provided.
- Tools (`nextcopy`, `nextdump`) and Fortran bindings are planned for v4.1.0, not v4.0.0.

---

## Breaking Changes

None. v4.0.0 is additive: a new UDF slot, a new backend, and new NetCDF type constants. Existing NEP handlers and build configurations are unchanged when `NEP_ENABLE_NEXTCDF4` is disabled.
